# Security review — M1-2

STATUS: CLEAR

Reviewed: registration / login / forgot-password / reset-password UI
(client pages + one auth.ts flag + test7), against all seven iron rules.
Reviewer read every in-scope file in full, plus the better-auth 1.7.x
source backing each security claim the pages make in their comments.

## Checked

- PCI scope: no payment code path touched. No card data handled, logged
  or stored in any in-scope file. No finding.

- Payment idempotency: no webhook handlers in scope. Adjacent replay
  concern checked instead — the reset token is single-use
  (`consumeVerificationValue`, node_modules/better-auth/dist/api/routes/
  password.mjs:158), so a replayed or double-submitted reset POST fails
  closed with INVALID_TOKEN. No finding.

- Auth: no hand-rolled credential field, no custom JWT, no custom session
  table. All four pages POST to better-auth endpoints only; no client-side
  hashing, no direct DB writes, no bespoke validation. AHD8 upheld.
  * Criterion 1 (login enumeration) VERIFIED: login/page.tsx:36-45 has one
    request, one error branch, renders body.message verbatim, no pre-check.
    sign-in.mjs:320-338 returns identical UNAUTHORIZED /
    INVALID_EMAIL_OR_PASSWORD for not-found, credential-less and
    wrong-password, with a dummy password.hash() on both not-found paths
    (timing side-channel closed). test7:154-159 asserts status+code+message
    equality, not merely that an error rendered.
  * Criterion 2 (forgot-password enumeration) VERIFIED and stronger than
    required: forgot-password/page.tsx:49-52 never reads res.json() and
    renders a hardcoded const on any 2xx, so it cannot leak a divergent
    body even if the API later regressed. Server side identical at
    password.mjs:69-72 vs 88-91.
  * Criterion 3 (revokeSessionsOnPasswordReset) VERIFIED actually set at
    src/lib/auth.ts:47 and actually effective — password.mjs:173 gates
    deleteUserSessions(userId) on it. test7:246-292 proves Session A works
    against real /profile before the reset and is dead after (both DB row
    and live HTTP).
  * Criterion 4 (no token leak) VERIFIED: token goes query string ->
    server component (reset-password/page.tsx:18) -> prop -> POST body
    only. No console.*, localStorage, sessionStorage or document.cookie
    anywhere under src/app/auth/ (grepped). Reset errors come from
    BASE_ERROR_CODES constants (password.mjs:151-162) with no token
    interpolation, so no token can surface in a message.
  * No admin routes in scope.

- Secrets: no env files changed; no literal secret introduced anywhere in
  the diff. M1-1's sendResetPassword hardening is intact (src/lib/auth.ts:
  36-40) — non-production guard still present, callback still destructures
  `{ url }` only. No finding.

- Admin audit log: no admin mutations in scope. No finding.

- Input validation: server-side Zod on every endpoint these pages call
  (z.email(), z.string()); reset password min/max length enforced
  server-side at password.mjs:153-156. Forms are noValidate with client
  minLength={8}, so client rules are bypassable by design — server is
  authoritative on every path, which is the correct arrangement. No
  finding.

- Data residency: nothing region-routing in scope. redirectTo is derived
  from window.location.origin client-side AND independently origin-checked
  server-side (password.mjs:50 and :97), so it cannot be pointed at an
  attacker origin to exfiltrate the reset token. No finding.

## Red-team attempts that did not land
- Open-redirect reset-token exfiltration via a directly-POSTed hostile
  `redirectTo` — blocked by originCheck on both the POST and GET callback.
- Bypassing client-side password rules via noValidate — server enforces
  independently.
- Replaying a consumed reset token — single-use, fails closed.
- Rolling own validation in the reset flow — does not occur; newPassword
  always goes through better-auth's own endpoint.

## Non-blocking observations (do not block the gate)
- src/app/auth/register/page.tsx:38-40 renders body.message verbatim, and
  sign-up.mjs:212 returns 422 "User already exists. Use another email." —
  so the registration form distinguishes registered from unregistered
  emails even though login and forgot-password deliberately do not.
  Outside M1-2's stated criteria and common practice, but the hardening on
  the other two forms is only as strong as the weakest form. Recommend
  product-planner either accept this explicitly on the ledger or schedule
  it for M1-3.
- vitest.config.mts:54 adds src/app/auth/** to the coverage excludes. The
  subprocess-coverage justification genuinely applies to test7, but the
  exclusion list is growing and the config's own comment warns against
  exactly that. Measurement gap, not a testing gap — flagged for the gate.

## Known limits (could not assess without running code)

- The sign-in timing-attack mitigation is asserted from reading
