## Advisories (LOW, non-blocking — no fix required to pass this gate)

**A1 — `[orderId]/page.tsx:29-75`: ownership check is split from the
read; another tenant's PII is materialized before the check runs.**
The page does `findUnique({ where: { id: orderId } })` selecting the full
`shippingAddress` (`fullName`, `phone`, `street`, `city`, `postalCode`)
and all `items`, and only then compares `order.userId` at line 73. The
check is correct today and `notFound()` throws before any render, so
nothing leaks to the response. Two residuals: (a) another customer's PII
is loaded into server memory on every non-owner request, so any future
edit that logs/serializes `order` before line 73 becomes an instant
disclosure; (b) a marginal timing oracle — a nonexistent id costs one
missed lookup while an existing-but-not-yours id pays the full
address/items/events joins, both returning 404. Not practically
exploitable (order ids are cuids, unguessable). Preferred shape, per this
repo's own documented single-statement-enforcement rule:
`db.order.findFirst({ where: { id: orderId, userId: session.user.id } })`
followed by `if (!order) notFound()` — closes both residuals at once and
removes the need for `userId` in the `select`.

**A2 — `page.tsx:36`: `where: { userId: session.user.id }` relies on an
unstated invariant that `session.user.id` is never `undefined`.**
Prisma treats an `undefined` value in a `where` clause as "filter
absent", so if `session.user.id` were ever `undefined` this query would
silently become `findMany({})` and render EVERY order in the table,
across all tenants, to the requester. Not reachable today: `!session` is
guarded at line 31 and better-auth always populates `user.id` — and TS's
non-nullable typing means the compiler would not catch a regression here
either. This is a "does not leak" resting on an external library
invariant rather than a local one. Cheap hardening: an explicit
`if (!session?.user?.id) redirect("/auth/login")`. The same note applies
to `[orderId]/page.tsx:73`, though there the failure mode is safe
(`order.userId !== undefined` is true → `notFound()`).

**A3 — `src/lib/money.ts:10`: the shared formatter silently drops the
cents from every snapshot amount it renders.**
`new Intl.NumberFormat("en-US")` with no options defaults to
`minimumFractionDigits: 0`, so a `toFixed(2)` snapshot renders lossily:
`"53922.00"` → `"KES 53,922"` and `"1210.50"` → `"KES 1,210.5"`. The unit
test at `test27:96-98` codifies this behaviour rather than catching it.
This is a pre-existing repo-wide convention, copied verbatim, not
invented here — identical expressions live at `CartSummary.tsx:16`,
`CartLineItems.tsx:10`, `ReviewStep.tsx:19`,
`VariantSelector.tsx:127` — so this is not a regression. Raising it
anyway for two reasons specific to this item: (i) M5-1b is the first
surface that displays what the customer was *actually charged* (a
durable snapshot), not a live catalog price; and (ii) M5-1a's
confirmation email formats the same order via
`src/emails/orderConfirmation.ts:50-52`, which preserves the string
verbatim — so the same order reads `KES 1210.00` in the email and
`KES 1,210` on the dashboard. No money-path effect whatsoever (the
`Decimal(12,2)` snapshot columns and everything charged are correct;
this is display only, and `Number()` here is applied to a bounded
`toFixed(2)` string, well under `2^53`, so no precision is lost). Since
`money.ts` is now the shared extraction point, fixing it here
(`{ minimumFractionDigits: 2, maximumFractionDigits: 2 }`) would fix all
callers at once — worth a tracked follow-up, not this gate's business.

**A4 — `test27:283-286`: the forged-cookie test derives the cookie name
positionally, so a drift would silently degrade it into the no-cookie
path.** `signUpAndSignIn()` joins ALL `Set-Cookie` pairs into one header,
and the test then takes `cookieHeader.split("=")[0]` — i.e. whichever
cookie better-auth happens to emit FIRST. Correct today, and the value is
runtime-derived (the important half — no hardcoded name, matching
`test6:206`). But if better-auth ever emits a non-session cookie first
(e.g. a session-data/cache or CSRF cookie), the forged header would carry
the wrong name, `getSessionCookie()` in middleware would find nothing and
redirect — and the assertion (`pathname === "/auth/login"`) is
byte-identical to the no-cookie test's assertion at `:269-277`, so the
test would still pass while no longer proving anything about the
page-level check. This is precisely the failure mode this repo's own
learnings entry warns about, arriving through a different door than a
hardcoded name. Suggested hardening: select the pair whose name contains
`session_token` rather than taking index 0. Non-blocking because the
builder documented the neutralize-and-rerun proof
(`FEATURES.md:3252-3254`, `:3298-3300`), which establishes the test is
currently reaching the page's own check.
