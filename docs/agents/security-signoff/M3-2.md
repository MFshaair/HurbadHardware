## The eight questions asked

### 1. The F8 fix — VERIFIED correct, and the regression test is genuinely non-trivial
`src/lib/cartService.ts:306-308`: the guest branch is now
`findFirst({ where: { sessionId, userId: null, expiresAt: { gt: now } } })`.
Not merely present — enforced, and not bypassable:

- I grepped every `sessionId` predicate in the file. The only other
  `sessionId`-keyed lookups are `getOrCreateCart`'s stale-row
  `deleteMany` (`:352-354`, additionally scoped `expiresAt <= now`, so it
  can only delete an already-dead row) and `mergeGuestCartOnLogin`
  (`:583`), which does its own explicit cross-owner guard at `:597`
  (`guestRow.userId && guestRow.userId !== userId` → falls back to the
  requester's own cart). The M3-1 F2 race-loser guard at `:389-391` is
  also still intact.
- No caller reaches the old unguarded shape: every consumer
  (`src/app/api/cart/{route,add,update,remove}`, `src/app/cart/page.tsx`,
  `src/app/checkout/checkoutCart.ts`) goes through `findActiveCart`/
  `getOrCreateCart`, never a raw `shoppingCart.findFirst` of its own
  (verified by grep, not assumption).
- The regression test (`tests/test17-reservation.test.ts:150-175`) is
  structurally incapable of passing with the fix removed: it creates a
  cart with **both** `sessionId` and a real `userId`, then calls
  `findActiveCart({ sessionId })` with no `userId` and asserts `null`.
  Delete `userId: null` from `:307` and that `findFirst` matches the row
  and returns non-null → the test fails. The companion case at `:165-174`
  proves the filter didn't just break guest lookups outright, so it is
  not a trivially-green assertion pair. This is the "prove it can fail"
  standard, satisfied by construction rather than by claim.

M3-1 F8 / M3-3a F5 are hereby **closed**.

### 2. Raw SQL injection safety — checked, no finding
Every raw statement in `reservationService.ts` is a Prisma tagged template
(`tx.$queryRaw`/`tx.$executeRaw`/`db.$queryRaw`), never `$queryRawUnsafe`/
`$executeRawUnsafe` (grep: zero `Unsafe` occurrences repo-wide in this
diff). All eleven sites verified individually: `:170`, `:176`, `:238`,
`:356`, `:381`, `:474`, `:561`, `:569`, `:580`, `:615`, `:654`, `:672`.
Every interpolated value is a `${}` parameter binding, and none is
concatenated into the SQL text.

`IN` lists use `Prisma.join()` per ADR Decision 3, not manual string
building: `:359` (`Prisma.join(variantIds)`), `:563` and `:617`
(`Prisma.join(inventoryIds)`). `Prisma.join` emits one placeholder per
element, so the ids remain bound parameters. Both empty-array cases are
excluded upstream (`items.length === 0` throws `EmptyCartError` at `:340`;
`reservations.length === 0` returns early at `:556`; `:614` guards
`inventoryIds.length > 0`), so no `IN ()` syntax error path exists.

The `${region}::"Region"` cast (`:360`): `region` is `cart.region`, read
from the `ShoppingCart` row inside the same transaction (`:238-243`),
typed `Region` (the Prisma enum) via `LockedCartForOrder` at `:219`. It is
**never** the caller's — `CreateReservationAndOrderInput` (`:188-198`) has
no `region` field at all, so no HTTP body value can reach it. Even if it
could, it is a bound parameter; the `::"Region"` cast is applied to the
placeholder, not to spliced text, so a non-enum value would produce a
Postgres cast error inside a transaction that rolls back, not injection.
Same reasoning holds for the `::"ReservationStatus"` casts, whose values
are either string literals in the SQL text or the TypeScript-narrowed
`"RELEASED" | "EXPIRED"` union at `:153`.

### 3. Cross-user address access — VERIFIED by reading the resolution code
`src/lib/reservationService.ts:345-348`:
`tx.address.findFirst({ where: { id: input.shippingAddressId, OR: [{ userId: input.userId }, { userId: null }] } })`,
`AddressNotFoundError` (→ 404 with a generic body, `:131-134`) otherwise.
This is exactly the M3-3a-established pattern: the id is re-checked
against the server-side session's user, guest-owned (`userId: null`) rows
stay reachable per `Address.userId`'s nullability, and a row owned by a
*different* user is unreachable. The check runs **inside** the same
transaction that creates the `Order`, so it is not a TOCTOU split across
connections. `input.userId` is documented at `:192-196` as required to
come from a server-side `auth.api.getSession()`, never the client — that
contract is currently unenforced only because no route exists yet (see
F2).

Red-teamed: authenticated attacker + victim's address id → covered by the
test at `:577-591`, which asserts `AddressNotFoundError`. Guest
(`userId: null`) + a *user-owned* address id → `OR: [{userId: null},
{userId: null}]`, no match, rejected. Guest address + authenticated
checkout → deliberately allowed, tested at `:593-606`. Non-existent id →
404, same shape as cross-user, so no existence oracle.

### 4. Money computation integrity — checked, no finding
`CreateReservationAndOrderInput` (`:188-198`) carries **no** amount, no
currency, no tax rate, no region, no shipping figure — the type itself
makes caller-supplied money unrepresentable. Inside the transaction
(`:416-438`): `unitPrice` comes from `tx.regionalPrice.findFirst({
variantId, region: cart.region })` (missing row → `PriceUnavailableError`,
never a fallback price); `totalPrice = price.price.mul(quantity)`;
subtotal is accumulated in integer cents; `taxCents = round(subtotal *
getTaxRate(cart.region))` from `src/lib/tax.ts`'s pure region→rate map;
`shippingAmount` is a hardcoded `new Prisma.Decimal(0)`. The `Order.create`
at `:442-455` writes only those computed values plus `region`/`currency`
read from the **cart row**, not the input. `OrderItem.createMany`
(`:457-465`) writes only `orderItemsData`, built entirely from
`RegionalPrice`. Test `:620-636` pins 3 × 1000.00 → 3000.00/480.00 (16%
KE VAT)/3480.00/0.00.

The only caller-supplied non-money fields that reach the DB are
`shippingAddressId` (ownership-checked, #3), `userId` (server-derived by
contract), `guestEmail` (PII stored on the order it belongs to, never
logged), and `paymentProvider` (allowlisted against a literal union at
`:521-523` before any DB work — tested at `:538-549`).

`orderNumber` (`:255-259`): `HH-<Region>-<Date.now() base36>-<3 random
bytes hex>`. No PII, no user id, no email, no cart id. The timestamp
component is sequential-ish, but 24 bits of `node:crypto` CSPRNG suffix
means enumerating a neighbouring order requires ~16.7M guesses *per
millisecond bucket*, and — more importantly — this repo has no
order-lookup-by-number route today, so there is nothing to enumerate
against. Acceptable. Note for M5: if a "track my order by number" page is
ever built, it must not treat `orderNumber` as a bearer secret.

### 5. Cron route authentication — checked, no finding
`route.ts:18-30`. `crypto.timingSafeEqual`, not `===`. The
mismatched-length hazard is handled correctly and in the right order:
`:27` returns `false` on `headerBuf.length !== expectedBuf.length`
**before** `:29` calls `timingSafeEqual`, so the `RangeError` that Node
throws on unequal-length buffers can never be reached — no unhandled
exception, no 500, no crash. (Length is inherently observable regardless;
that is intrinsic to any comparison and not a finding.) Fails closed on
an unset secret: `:20` `if (!secret) return false` runs before anything
else, and an empty-string `CRON_SECRET` is also caught by the same falsy
check — an empty secret cannot degrade into "compare `Bearer ` to
`Bearer `" and pass. A missing header becomes `""`, whose length differs,
→ 401. Tests `:643-664` cover both the unset-secret and wrong-token legs
and assert 401.

`export const dynamic = "force-dynamic"` (`:9`) prevents the response
being served from a static/ISR cache, which matters here because a cached
200 would otherwise be reachable without the header.

### 6. Double-submit / idempotency — checked, no finding
The mechanism is sound because the **cart row lock is the first statement
in the transaction** (`:321` → `lockCartForOrder`, `:238-243`, a bare
`SELECT ... FOR UPDATE` with no `expiresAt` filter — deliberately unlike
`cartService.lockCart`, and correctly so, since a consumed cart must still
be lockable for the idempotent lookup to run). A concurrent duplicate
submit blocks on that lock, and under Read Committed re-reads the row
after the winner commits, so it sees `expiresAt <= now` (`:326`) and takes
the idempotent path. There is no window in which two transactions can both
pass `:326` and both reach `tx.order.create` — reaching `create` requires
holding the cart lock, and the winner sets `expiresAt = now` (`:504`)
before releasing it. Test `:295-332` drives this with a real `Promise.all`
and asserts exactly one `Order`, exactly one `CREATED` `OrderEvent`, one
reservation row, and `reserved === 2` not `4`.

The `OrderEvent` lookup (`:330-333`) uses Prisma's structured JSON filter
`payload: { path: ["cartId"], equals: input.cartId }` — a bound parameter
through the query engine, **not** raw string interpolation into a
`jsonb` path expression. No injection surface.

Red-teamed further: replaying the same call *after* both complete → cart
still consumed → idempotent return of the same order, no second
reservation. Replaying with a *stale* cart that expired naturally without
an order → no `CREATED` event → `CartNotFoundError` (404), fails closed
rather than creating a second order. Transient-retry path (`:525-538`) →
a rolled-back attempt commits nothing, so the retry cannot see its own
half-written state. `confirmReservationsForOrder` is itself replay-safe
via the CAS at `:569-577` (`affected !== 1` → throw, no double
`onHand` decrement) and `releaseReservationsForOrder` via `casRelease`'s
`AND status = 'ACTIVE'` + `GREATEST(0, ...)` clamp — the two properties
M4's webhook will depend on.

## Findings

### F1 (MEDIUM — same timezone bug class, fixed in the new file, still live in two untouched sites)
The builder correctly diagnosed that a bare SQL `now()` (timestamptz)
implicitly cast to a `timestamp without time zone` column adopts the DB
**session's** `TimeZone` GUC, and fixed it everywhere in
`reservationService.ts`. Two sites in the same class remain:

- `src/lib/cartService.ts:267` (`lockCart`):
  `WHERE id = ${cartId} AND "expiresAt" > now()` — bare `now()` compared
  against the naive-UTC `ShoppingCart.expiresAt`.
- `prisma/schema.prisma:164`:
  `@default(dbgenerated("(now() + '7 days'::interval)"))` — the same
  implicit cast at INSERT time, so the cart TTL is minted skewed by the
  session offset.

Both are **pre-existing** (M3-1/M0) and **not introduced by M3-2**, so
they do not block this item. The reason they are MEDIUM rather than a
footnote is that M3-2's idempotency mechanism now *depends* on the
`expiresAt > now()` predicate being correct everywhere: Decision 9
consumes the cart by setting `expiresAt = now` (`:504`), relying on
"every `cartService.ts` read filters `expiresAt > now()`" (its own comment
at `:500-503`). On a DB session whose timezone is *behind* UTC (e.g. any
`America/*`), bare `now()` yields a naive timestamp N hours in the past,
so `lockCart` would still treat an **already-consumed** cart as live —
letting a shopper keep mutating a cart that has already been converted to
an `Order` with stock reserved against it. The same offset direction also
extends a leaked guest-cart cookie's usable lifetime past its intended
TTL.

Not exploitable in the current deployment (RDS/Postgres defaults to UTC,
and no route reaches `createReservationAndOrder` yet), and local dev's
documented `Africa/Mogadishu` (+03) skews in the *safe* direction. But
"correct only because the DB happens to be UTC" is exactly the class of
unstated global invariant that breaks silently. Fix `cartService.ts:267`
to `(now() AT TIME ZONE 'UTC')` and either migrate the schema default the
same way or set the connection's `timezone=UTC` explicitly.
**Routing: `catalog-inventory-engineer`. Binding on M3-3.**

### F2 (MEDIUM-advisory — `createReservationAndOrder` never checks cart ownership)
`src/lib/reservationService.ts:321-337`. The function locks and consumes a
cart **by id alone**. It reads `cart.userId` and `cart.sessionId`
(`:238-243`, and writes `sessionId` into the `OrderEvent` payload at
`:496`) but never compares either against `input.userId` or the
requester's session cookie — unlike the address parameter three lines
later, which is correctly ownership-checked. The ADR's Decision 5
(`:173-182`) specifies the ownership check for `shippingAddressId` and is
silent on `cartId`, so this is a gap in the design, not a deviation from
it.

Consequence if M3-3 wires a route that reads `cartId` from the request
body: an authenticated caller supplying another shopper's `cartId` would
consume that cart, reserve that shopper's stock, and create an `Order`
under the attacker's own `userId` with the victim's line items —
griefing/inventory-denial plus disclosure of the victim's cart contents
and totals. Exploitation presupposes knowing a `cartId` (a high-entropy
cuid, not enumerable), and **no such route exists today**, which is why
this is not blocking.

Two defences, both cheap, ideally both: (a) M3-3's route must derive
`cartId` server-side from `findActiveCart({ sessionId, userId })` and
never accept it from the body — the pattern
`src/app/api/cart/route.ts:12` already documents for this repo; and (b)
`createReservationAndOrder` should assert
`cart.userId === input.userId || cart.userId === null` (and, for a guest,
that `cart.sessionId` matches the presented cookie) and throw
`CartNotFoundError` otherwise, so the invariant is local to the money
function rather than resting on every future caller's discipline — the
"prefer single-statement/local enforcement over a global invariant" rule
from my own learnings. **Routing: `catalog-inventory-engineer` for (b);
binding on `storefront-admin-engineer` for (a) when M3-3 is built.**

### F3 (LOW — the idempotency lookup is a cart-id-keyed order oracle)
`:330-336`. Anyone who can supply a consumed `cartId` gets back the full
`ReservationOrderResult` for the associated order: order id, order number,
subtotal, tax, total, payment status. No ownership predicate is applied to
either the `OrderEvent` lookup or the `findUniqueOrThrow` on `Order`. Same
root cause and same mitigation as F2 — fixing F2(b) closes this too, since
the ownership assertion happens before the idempotent branch is reached.
Recorded separately so the fix isn't scoped to the create path only.

### F4 (LOW — informational leakage in two error bodies, plus a committed dev cron secret)
- `:115-120`: `ReservationNotActiveError` is returned to the client with
  `err.message` **and** `reservationId` **and** the internal reservation
  `status` in the body. Internal row ids and state-machine values should
  not cross the boundary; the M3-1 F6 pattern applied elsewhere in this
  same function (log the id, return a generic body) should apply here too.
  Only reachable from M4's webhook path, hence LOW.
- `:102-111`: `InsufficientStockError` returns `availableForSale` to the
  client. This discloses exact per-variant stock levels to any shopper.
  Established in M3-1 and arguably deliberate UX, so not new — noted only
  so it is a decision rather than an accident.
- `.env.development:39` commits a real (if deliberately worthless) value
  for `CRON_SECRET`. Anyone running a preview/dev deployment off that file
  has a publicly-known cron secret. Blast radius is small — the route only
  releases *already-expired* reservations and is idempotent — but any
  environment reachable from the internet must override it.

### F5 (LOW — a lock guarantee the comment claims but the code does not provide)
`:654-660`. The candidate scan runs `FOR UPDATE SKIP LOCKED` via
`db.$queryRaw` **outside** any transaction, so Postgres autocommits and
releases those row locks the instant the statement returns. The comment at
`:641-649` describes `SKIP LOCKED` as preventing overlapping invocations
from colliding — it does not; two concurrent cron runs will select
overlapping candidate sets. This is harmless in practice because the real
guard is `casRelease`'s `AND status = 'ACTIVE'` + `affected === 1`, which
is what actually makes double-release impossible (and the `:699-706`
idempotency test exercises it). But the comment overstates the mechanism,
which is how a future editor ends up removing the CAS believing the lock
covers it. Either wrap the scan in the transaction or correct the comment.
**Routing: `catalog-inventory-engineer`, non-blocking.**
