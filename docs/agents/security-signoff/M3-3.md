## Checked

- **PCI scope:** no finding. Nothing in the diff handles, logs, or stores card
  data. `POST /api/checkout` imports no payment SDK (`route.ts:1-13` — no
  `stripe`, no `mpesa`); `paymentProvider` is a two-value string label only,
  persisted to `OrderEvent.payload` (`reservationService.ts:521`). No
  `PaymentTransaction` row is created. Grepped the new/changed files for
  card-shaped literals and credential names — none.
- **Payment idempotency:** no finding, and this is genuinely enforced rather
  than claimed. No webhook handler exists yet (M4), but the double-submit
  equivalent is real: `attemptCreateReservationAndOrder` locks the cart
  `FOR UPDATE` with no `expiresAt` filter (`reservationService.ts:240-251`),
  short-circuits on an already-consumed cart by looking up the `CREATED`
  `OrderEvent` keyed on the server-derived `cartId`
  (`:347-358`), and consumes the cart inside the same transaction (`:529`).
  Stock cannot be double-decremented: `onHand` is untouched at reservation
  time and `casRelease`'s `AND status = 'ACTIVE'` + `affected === 1` guard
  (`:170-183`) makes double-release impossible. Proven end-to-end through the
  route by two genuinely concurrent requests on the same cart cookie
  (`tests/test18-checkout.test.ts:301-356`), asserting exactly one `Order`,
  one set of `OrderItem`s, and exactly one `idempotent:false` winner — not a
  sequential resubmit that would trivially 404.
- **Auth:** no finding. No hand-rolled credential field, no custom JWT, no
  custom session table. `route.ts:88` uses `auth.api.getSession({ headers:
  await headers() })` — the same better-auth call the rest of the repo uses —
  and `userId` is `session?.user.id ?? null`, never read from the body. No
  admin route is added, so admin role-verification is not in scope here.
  Presence-check middleware: `src/middleware.ts` matches `/profile/:path*`
  only; neither `/checkout/*` nor `/api/checkout` is behind it, so there is no
  new presence-only gate to forge past. Guest checkout is intentionally
  unauthenticated and the route derives all identity server-side.
- **Secrets:** no finding. No literal value introduced in any file; no `.env`
  file touched. Nothing logs a secret or PII: the only logging on this path is
  `reservationErrorResponse`'s `console.error` of a cart/address **id**
  (`reservationService.ts:128,132`) with a generic client-facing message.
  `ReviewStep.tsx` logs nothing. (Informational, pre-existing from M3-2, not
  worsened here: `OrderEvent.payload` stores the guest cart `sessionId`
  (`:521`), which is effectively a bearer value for that guest cart — worth
  keeping out of any future admin order-event UI.)
- **Admin audit log:** N/A, checked not skipped. This diff adds no admin
  mutation and no admin route; `AdminAuditLog` is not referenced anywhere in
  the changed files. Nothing here should have written to it.
- **Input validation:** mostly holds; see F2. Every client-supplied field is
  validated server-side before use: body must be a JSON object
  (`route.ts:100-108`); `paymentProvider` against a two-value literal
  allowlist (`:111-113`) *and* independently re-checked against
  `VALID_PAYMENT_PROVIDERS` in `createReservationAndOrder`
  (`reservationService.ts:546-548`); `addressMode` against
  `"saved" | "new"` with an explicit `else` 400 (`route.ts:155-157`);
  `savedAddressId` type+length-checked (`:119-124`); `newAddress` passed

  `db.address.create` (`:138-141`) — I traced the control flow, there is no

## Targeted questions from the dispatch

### 1. `cartId` derivation — VERIFIED, traced, not taken on trust
`route.ts` has exactly two `cartId` sites and neither touches the body.
`const cart = await findActiveCart({ userId: userId ?? undefined, sessionId })`
(`:92`), then `cartId: cart.id` (`:161`). `cartId` does not appear in the
`CheckoutRequestBody` interface (`:15-21`), and `body`/`draft` is only ever
read for `paymentProvider`, `addressMode`, `savedAddressId`, `newAddress`,
`saveNewAddress` — I checked every `draft.` dereference in the file. There is
no later overwrite; the value is a `const` derived before the body is even
parsed (the `!cart` 404 at `:93-98` short-circuits before `request.json()`).
Both inputs to `findActiveCart` are server-derived: `userId` from
`auth.api.getSession()`, `sessionId` from `getCartSessionId()` reading the
`httpOnly` cart cookie (`cartCookie.ts:51-54`). The cross-guest test at
`tests/test18-checkout.test.ts:455-504` is non-trivial: it plants a real
victim `cartId` *and* a `userId` in the body, asserts the resulting order's
subtotal is the attacker's `10.00` rather than the victim's `999.00`, asserts
the order line is the attacker's variant, and asserts the victim's cart is
still active and still resolvable by the victim's own cookie. That is an
assertion that fails if the guard is removed, not a shape check.

### 2. Ownership assertion in `reservationService.ts` — VERIFIED enforced, no oracle
`:338-343` runs immediately after `lockCartForOrder` and **before** every
mutation and before the idempotent-lookup branch at `:347` — I traced the
statement order; there is no `tx.` write, no `orderEvent.findFirst`, and no
`order.findUniqueOrThrow` between the lock at `:327` and the check. That
ordering is what closes F3: a stranger's *consumed* cart cannot be used to
read back another shopper's order totals, because the throw happens before the
idempotent lookup. Truth table walked by hand:
- guest caller (`userId: null`) + cart owned by user B → `ownedByCaller` false → throws. Correct.
- authenticated A + cart owned by B → false → throws. Correct
  (`tests/test17-reservation.test.ts:649-676`).
- guest caller + guest cart with a different `sessionId` → `ownedByCaller`
  true but `guestSessionMatches` false → throws (`:678-698`).
- genuine owner (auth own cart; guest matching sessionId) → passes (`:700-...`).

Error contract: it throws `new CartNotFoundError(input.cartId)` — the
identical class and constructor argument as the "cart id never existed" path
at `:328` — which `reservationErrorResponse` maps to `404 { error: "Cart not
found" }` (`:127-130`), byte-identical in both cases. The id only ever reaches
`console.error`, never the client. No cart-existence oracle. The route's own
"no active cart at all" path (`route.ts:94-97`) deliberately routes through
the *same* `reservationErrorResponse` mapping rather than hand-writing a body,
so that response is identical too — good, that is the "cannot leak" shape, not
"does not leak".

One gap in this check, recorded as F2 below: the `input.sessionId ===
undefined` disjunct at `:340` disables guest-cart ownership verification
entirely for callers that omit `sessionId`.

### 3. Guest address creation — VERIFIED, no unauthenticated write of a user-attached row
`route.ts:151-153`: `userId: session && saveNewAddress ? session.user.id : null`.
Traced both operands. `session` is the return of `auth.api.getSession()` at
`:88` — a server-side verified session object, not a body field and not a
boolean the client can influence; `saveNewAddress` is `draft.saveNewAddress
=== true` (`:143`), a strict identity check, so `"true"`, `1`, or `{}` all
yield `false`. The `userId` written is `session.user.id`, never
`draft.userId`/`body.userId` (there is no such read anywhere in the file). If
the session check fails or is absent, the ternary's `session &&` operand is
falsy and the row is created with `userId: null` — it can therefore never
appear in the `userId`-scoped `GET /api/addresses` list
(`api/addresses/route.ts:22-25`) nor be readable via `GET
/api/addresses/[id]`, which requires `existing.userId === session.user.id`
(`api/addresses/[id]/route.ts:28`). A spoofed session is not a distinct case:
there is no client-controlled path into `session` at all. Test coverage is
real on both legs (`tests/test18-checkout.test.ts:394-451`) including the
"authenticated but box unchecked → `userId: null` and absent from the list"
leg, which is the one that would silently regress.

### 4. `paymentProvider` validation — VERIFIED, defense in depth
Allowlisted twice before it can reach `OrderEvent.payload`: `route.ts:111-113`
rejects anything but the two string literals with a 400 *before* any DB write
happens, and `createReservationAndOrder` re-checks against
`VALID_PAYMENT_PROVIDERS` (`reservationService.ts:37,546-548`) so a future
internal caller cannot bypass the route's check. The `as PaymentProvider` cast
at `route.ts:114` is only reached after the literal comparison narrows the
value, so it is not a type-assertion hole. An arbitrary string cannot land in
`payload.paymentProvider`. Negative test at
`tests/test18-checkout.test.ts:228`.

### 5. Money integrity — VERIFIED, no request-body field reaches any amount
Traced the whole response construction. The 201 body is `toResult(order,
...)` (`reservationService.ts:280-294`), whose every field is read off the
`Order` row Prisma just returned — `subtotalAmount`/`taxAmount`/
`shippingAmount`/`totalAmount` are `Prisma.Decimal.toFixed(2)` of the
persisted columns. Those columns are computed inside the transaction from
`RegionalPrice.price × CartItem.quantity` in integer cents (`:437-459`), with
`taxRate = getTaxRate(cart.region)` and `shippingAmount = new
Prisma.Decimal(0)`. The route passes exactly five inputs to
`createReservationAndOrder` (`route.ts:160-167`): `cartId` (server-derived),
`shippingAddressId` (an id, ownership-checked, never an amount),
`paymentProvider` (allowlisted label), `userId` (session), `guestEmail`
(`session?.user.email`), `sessionId` (cookie). No amount, currency, quantity,
tax rate, or region crosses that boundary — the route never even reads such a
field from the body. `ReviewStep.tsx` renders only `orderResult.*` from the
response; it never sends or echoes a price.

### 6. `suppressNextWriteRef` — VERIFIED security-neutral, no stale-PII window
`clearDraft` (`CheckoutDraftContext.tsx:97-101`) calls `clearCheckoutDraft()`
*first* — a synchronous `sessionStorage.removeItem` (`checkoutDraft.ts:157-164`)
— and only then sets the ref and the state. So the key removal is
unconditional and does not depend on the flag; the flag can only ever *skip a
write*, never restore one. There is no window in which the old address
reappears: the effect at `:64-71` either skips (flag set) or writes
`emptyDraft()`, and `emptyDraft()` contains no `newAddress`/`savedAddressId`
at all. The flag also cannot wedge a legitimate clear, for the same reason
(the removal precedes it). It is self-resetting on the very next effect run,
and `setDraft(emptyDraft())` always passes a fresh object identity so React
cannot bail out of the re-render and strand the flag.

One theoretical stranding path exists and is not exploitable: the
`!hydratedRef.current` early-return at `:65` precedes the flag check at `:66`,
so a `clearDraft()` before hydration would leave the flag set and swallow the
first post-hydration write. Unreachable in practice (the `[]` hydration effect
runs before any user interaction can call `clearDraft`), and the failure mode
is fail-safe — *less* PII persisted, never more. Not a finding; noted so the
next editor doesn't reorder those two lines the wrong way.
The regression is genuinely under test: `tests/test16-checkout-ui.test.ts:380-441`
asserts the raw `sessionStorage` key is non-null before submit and `toBeNull()`
*after* the confirmation view has rendered — i.e. after the `[draft]` effect
has run, which is exactly the render where the old code re-persisted the key.
Reverting the ref makes that assertion fail; it is not a shape check.

### 7. Confirmation view — VERIFIED, no cross-user render
`ReviewStep.tsx:194-240` renders exclusively from `orderResult`, the parsed
body of *this browser's own* `POST /api/checkout` response (`:141`,
`setOrderResult(result)` at `:143`). There is no re-fetch by order id, no
`GET /api/orders/[id]`, no id in the URL, and no order id rendered at all —
only `orderNumber`, the four server-computed amounts, `currency`, and
`paymentStatus`. Since the response is produced from the requester's own
server-derived cart, another user's order cannot be reached: there is no
input to guess. The confirmation view also correctly suspends the redirect
guard (`:78`) instead of clearing the draft and bouncing the user, which
avoids an accidental resubmit loop.

## Findings

### F1 (MEDIUM, non-blocking) — `Address` row is created outside the transaction, orphaning PII on every failed or idempotent-replay checkout
`src/app/api/checkout/route.ts:151-153`. `db.address.create` runs *before*
`createReservationAndOrder` (`:160`) and is never rolled back or cleaned up
when that call throws. Every 409 (`InsufficientStockError`,
`PriceUnavailableError`, `ReservationConflictError`, `EmptyCartError`) and
every 404 (`AddressNotFoundError`) therefore leaves a permanent, ownerless
`Address` row holding `fullName`, `phone`, `street`, `city`, `postalCode`. It
is not only an error-path issue: on the **idempotent replay** the diff itself
tests (`tests/test18-checkout.test.ts:301-356`, an ordinary double-clicked
"Place order"), the losing request creates a second `Address` row and then
returns the *first* order — so the extra row is orphaned on the success path
too. Because `userId` is `null` on all of these, they are unreachable by
`GET /api/addresses`/`[id]`, so there is no user-facing deletion path and no
retention story.

Two aggravators, both verified: this is the first **unauthenticated**
reachable `Address` write in the repo (`POST /api/addresses` 401s without a
session, `api/addresses/route.ts:31-34`), needing only a guest cart cookie
plus one cart line; and `validateAddressBody` (`src/lib/addressValidation.ts`)
enforces no maximum length on any field while `model Address`
(`prisma/schema.prisma:431-436`) declares them as unbounded `String`/`text`,
so a single request can store an arbitrarily large blob. No rate limiting
exists on this route.

Not blocking: no cross-user access, no money impact, no auth bypass. But it is
a data-minimization and storage-amplification defect on the money path, and it
is the third recurrence of this class (M3-3a F3 flagged duplicate `Address`
rows from the address-step resubmit). Requirement for the fix owner
(`commerce-payments-engineer`): the `Address` row must not survive a failed
reservation — either create it inside the same transaction, or delete it
best-effort in the `catch` at `:169-175` and on the `idempotent === true`
branch — and `validateAddressBody` should grow per-field maximum lengths
(binding on M4 at the latest, since M4 adds more failure modes between the
address create and a confirmed order).

### F2 (LOW) — `isDefault` is client-settable through `newAddress`, bypassing the one-default-per-user invariant and unhandled at the DB
`src/app/api/checkout/route.ts:138-153`. The route's own doc comment
(`:48-51`) lists the `newAddress` fields as `fullName, phone, region, city,
postalCode, street`, but it passes the raw object to `validateAddressBody`,
which also accepts and returns `isDefault`
(`src/lib/addressValidation.ts:79-86`), and then spreads `...data` straight
into `db.address.create`. So an authenticated client sending
`{"newAddress": {...,"isDefault": true}, "saveNewAddress": true}` creates a
default address through the checkout route. Both address routes deliberately
wrap this in a transaction that first unsets the previous default and catch
the resulting `P2002` from the partial unique index
`address_one_default_per_user` (`api/addresses/route.ts:63-85`,
`[id]/route.ts:79-102`); this route does neither, so a user who already has a
default gets an **uncaught** `P2002` — thrown before the try/catch at
`:169`, so `reservationErrorResponse` never sees it — surfacing as a 500 on
"Place order" rather than a mapped error. Impact is self-scoped (a user can
only alter their own default) and the DB index still prevents two defaults, so
this is LOW, but it is mass-assignment of an undocumented field into a write
the route did not intend to expose. Fix: pass an explicit field allowlist (or
`isDefault: false`) at `:152`. Routing: `commerce-payments-engineer`.

### F3 (LOW, carried forward from M3-3a F2, still unfixed in a file this diff edited)
`src/app/checkout/review/ReviewStep.tsx:98`:
``fetch(`/api/addresses/${draft.savedAddressId}`)``. `savedAddressId` comes
from `sessionStorage` and is validated only as `typeof === "string"`
(`checkoutDraft.ts:85`); a `../`-bearing value normalizes to a different
same-origin endpoint before dispatch. Same bounded impact as recorded in
M3-3a's sign-off (writing the victim's `sessionStorage` already presupposes an
XSS on this origin, and the reachable endpoints are GET-only), so it remains
LOW and non-blocking — but this pass rewrote this file and did not apply the
one-word fix. Wrap it: `encodeURIComponent(draft.savedAddressId)`. Routing:
`storefront-admin-engineer`.

### F4 (LOW, advisory) — the service-level cart-ownership check has an `undefined`-sessionId escape hatch
`src/lib/reservationService.ts:339-340`:
`input.sessionId === undefined || cart.sessionId === input.sessionId`. When a
caller omits `sessionId`, guest-cart ownership is not verified at all —
`cart.userId === null` already satisfies `ownedByCaller`, so *any* guest cart
id would pass. Safe today only because the single caller
(`route.ts:92,166`) always derives both `cartId` and `sessionId` from the same
request and never accepts a `cartId` from the client — i.e. the guarantee is
the route's, not this function's, which is precisely the "unenforced contract
treated as a control" pattern that produced M3-2's F2 in the first place. The
input type's comment (`:199-203`) states the requirement in prose. Since F2(b)
exists specifically as the defense-in-depth layer for the *next* caller (M4's
webhook, or an internal retry job), it should fail closed: make `sessionId`
required, or reject when `cart.userId === null && input.sessionId ===
undefined`. Routing: `catalog-inventory-engineer`; binding on M4, the first
item to add a second caller.
