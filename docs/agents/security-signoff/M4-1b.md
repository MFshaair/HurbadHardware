## Checked

### 1. Signature verification as the entire trust boundary — HOLDS
- `route.ts:26` — `await request.text()` is the first statement of `POST`
  and the **only** body read in the file. There is no `request.json()`
  anywhere in the route, the service, or `stripe.ts`. Grepped: the only
  `request.*` reads in the route are `.text()` and
  `.headers.get("stripe-signature")` (`:27`).
- `src/middleware.ts:22` — matcher is `["/profile/:path*"]` only. It does
  not match `/api/webhooks/stripe`, and the middleware body never reads
  the request body at all (`getSessionCookie` only). Nothing in this repo
  can consume the stream before the handler. (If that matcher ever
  widens to `/api/*`, this guarantee breaks — the ADR flags this too.)
- **Zero DB access on a signature failure, confirmed structurally, not by
  test description:** `route.ts` imports only `next/server`,
  `@/lib/stripe`, and `@/lib/paymentWebhookService`. It has no `db`
  import, and `handleStripeWebhookEvent` (the only thing that touches
  Prisma) is called *after* `constructStripeWebhookEvent` returns
  successfully (`:31` then `:43`). `constructStripeWebhookEvent` itself
  performs no I/O — env read, header null-check, local HMAC-SHA256.
- **400 body is byte-identical across all four failure modes.** The
  literal `NextResponse.json({ error: "Invalid signature" }, { status: 400 })`
  at `route.ts:35` is the single 400 in the file, and it is reached for
  every `WebhookSignatureError`: missing header (`stripe.ts:160`),
  malformed header, wrong secret, tampered body, and stale timestamp
  (all wrapped at `stripe.ts:167-173`). No `err.message`, no field hints,
  no distinct status codes. Tests `test22:285-340` assert all four
  variants return exactly `{ error: "Invalid signature" }`.
- **Replay window intact:** `constructEvent` is called with the default
  300 s tolerance, not widened (`stripe.ts:166`); the stale-timestamp
  test (`:327`) proves a 1 h-old signature is rejected.
- **Failure logging does not leak.** `route.ts:34` logs Stripe's
  `err.message`. Verified against `node_modules/stripe/esm/Webhooks.js`
  (`:104,115,124,129,174,183,195`) that every
  `StripeSignatureVerificationError` message is a **constant string** —
  the header and payload are carried as separate error *properties*,
  never interpolated into `message`, and the secret never appears.

### 2. `charge.failed` is genuinely inert — CONFIRMED INDEPENDENTLY
Read the actual switch at `paymentWebhookService.ts:367-390`. It has
exactly four `case` labels — `checkout.session.completed`,
`.async_payment_succeeded`, `.async_payment_failed`, `.expired` — and a
`default: return { outcome: "ignored" }`. There is no `charge.*` or
`payment_intent.*` string anywhere in the module (grepped). No
state-changing branch is reachable for those types: `resolveRow` (the
first DB touch on any path) is only called from `handleConfirm`/
`handleFail`, both of which are only called from those four cases. A
`charge.failed` delivery therefore makes **zero DB calls of any kind**,
not merely zero writes. `checkout.session.completed` with
`payment_status !== "paid"` (`:370`) also returns before `resolveRow`.
Regression test `test22:498-524` asserts reservations stay `ACTIVE`,
`Order.paymentStatus` stays `PENDING`, tx stays `PENDING`.

### 3. Resumable confirm state machine — traced end to end
- (a) **Genuine duplicate is a clean no-op.** `confirmRow:133-141`:
  `row.status === "CONFIRMED"` → read `Order.paymentStatus` → if
  `CONFIRMED`, `return { outcome: "duplicate" }`. Only two `SELECT`s on
  that path; no `$executeRaw`, no `orderEvent.create`, no call into
  `reservationService`. Test `test22:347-367` asserts one
  `PAYMENT_CONFIRMED` event and `onHand` decremented exactly once.
- (b) **Already-flagged stock-gone does not double-write.** Two
  independent guards: `confirmRow:142-145` (`findStockUnavailableEvent`
  → `already_flagged`) and a second defensive check *inside*
  `recordStockUnavailable:246-249` covering the first-delivery
  `PENDING→CONFIRMED` path that never passed through `confirmRow`'s
  check. The lookup is scoped by both `orderId` **and**
  `payload.path(["paymentTransactionId"]) == row.id`, so a sibling
  attempt's flag cannot suppress this one's. Tests `:454-492` (sequential
  redelivery) and `:790-815` (two concurrent deliveries) both assert
  exactly one such `OrderEvent`.
- (c) **Crash-gap resume genuinely re-attempts.** `confirmRow:146-150`:
  when the row is `CONFIRMED` but the order is not, and no flag exists,
  it calls `runConfirm(...)` — it does not return `duplicate`. Test
  `:410-447` seeds exactly the post-crash state (tx `CONFIRMED`,
  reservations `ACTIVE`, order `PENDING`) and asserts outcome
  `"confirmed"`, `onHand` 10→8, reservation `CONFIRMED`, and that a
  further redelivery then reports `duplicate`. That test is
  non-trivial by construction: the naive "already CONFIRMED → no-op"
  implementation returns `duplicate` and fails it.
- **Post-condition assert is present and is not swallowed.**
  `runConfirm:213-222` re-reads `Order.paymentStatus` after *every*
  successful `confirmReservationsForOrder` call and `throw`s if it is not
  `CONFIRMED`; the throw propagates to `route.ts:45-48` → HTTP 500. It is
  not caught anywhere in between (the only `try/catch` in `runConfirm`
  closes at `:207`, before the assert). Test `:773-787` exercises the
  real zero-reservation silent-return path and asserts the loud throw
  plus `Order.paymentStatus` still `PENDING`.
- **`err.status` disambiguation:** `EXPIRED|RELEASED` → stock-gone
  (`:182`); `CONFIRMED` → re-read the durable order fact, `duplicate`
  only if the order really is confirmed, else throw → 500 (`:185-200`);
  any other status → rethrow, never guessed (`:201-204`).
- **Anomalous predecessors (`INITIATED`/`FAILED`/`CANCELLED`) throw**
  (`:153-158`) before any write. Test `:677-687`.

### 4. Row resolution — no cross-order/cross-tenant confusion
`resolveRow:66-69` resolves solely via
`findUnique({ where: { providerTxId: session.id } })`.
`providerTxId` is `String? @unique` (`schema.prisma:267`) and is written
exactly once, at session creation (`paymentService.ts:472-477`); this
diff never writes `providerTxId`. Crucially, **every downstream write
uses `row.orderId` / `row.id`, never `session.metadata.orderId` or
`client_reference_id`** — verified at `:121`, `:150`, `:183`, `:303`,
`:309`, `:334` — so even a maliciously crafted (but validly signed)
metadata field cannot redirect a confirm onto another customer's order.
Metadata is assertion-only: `metadata.paymentTransactionId !== row.id`
(`:78-83`) and `client_reference_id !== row.orderId` (`:85-90`) each log
ids only and `throw` **before** any write → 500, zero writes. Not
silently trusted, not silently ignored. No matching row → `null` → 200
`unknown_session`, zero writes (`:70-75`). Tests `:606-645` (incl. the
full signed-HTTP path asserting a real 500) and `:715-727`.

### 5. Money integrity — no amount re-derived from the payload
`confirmReservationsForOrder(orderId)` (`:179`) and

### 6. FAIL-path release guard — traced, not trusted
`failRow:282-326` → `releaseGuarded:334-348` is the **only** call site of

blocks:
1. `failRow:312-319` — the row's own status is `CONFIRMED` → `skipped`,

2. `releaseGuarded:335-341` — any *sibling* `PaymentTransaction` for the

## Findings

None blocking. Three non-blocking advisories, recorded for tracking (in
the same "tracked follow-up" class as M3-2's/M3-3's sign-offs):

**A1 — LOW — `src/lib/stripe.ts:161-173`: a missing `STRIPE_SECRET_KEY`
surfaces as a 400 "Invalid signature", contradicting ADR Decision 2.**
`getStripeClient()` is called *inside* the `try`, so its
`Error("STRIPE_SECRET_KEY is not set")` (`stripe.ts:11-13`) is caught and
re-wrapped as a `WebhookSignatureError`, which `route.ts:33-35` maps to
400. The ADR's binding rule ("a missing secret is a startup-class error,
not a 400") was implemented for `STRIPE_WEBHOOK_SECRET` — which is
checked before the `try` at `:158-159` and is tested (`test22:989-1013`) —
but not for its sibling. Not exploitable (the 400 body is still
byte-identical, so no oracle is created, and the site cannot create
sessions without that key anyway); the cost is diagnostic: a
misconfigured deployment 400s every delivery while the log says
"signature verification failed", sending ops after the wrong secret.
Fix: hoist `const stripe = getStripeClient();` above the `try` (HMAC
verification needs no API key — `Stripe.webhooks` is pure local crypto).
Owner: `commerce-payments-engineer`.

**A2 — LOW — `src/lib/paymentWebhookService.ts:334-347`: `releaseGuarded`
is a non-atomic check-then-act on the money path.** Both guards are plain
`SELECT`s outside any transaction; `releaseReservationsForOrder` then
opens its own. If a confirm delivery for a *sibling* `PaymentTransaction`
of the same order commits in the window between the guard reads and the
release transaction, `reservationService.ts:653` unconditionally sets
`Order.paymentStatus = 'FAILED'` on an order that was genuinely paid —
exactly the lie Decision 6's guard exists to prevent. Stock itself is
safe (`casRelease` no-ops on non-`ACTIVE` rows and the confirm holds
`RegionalInventory ... FOR UPDATE`), so this is an order-status
correctness risk, not an oversell risk, and it requires concurrent
confirm+fail deliveries for one order with two attempt rows — the exact
shape `test22:557-600` constructs sequentially. Durable fix belongs in
`reservationService.ts` (make the order write conditional, e.g.
`updateMany({ where: { id, paymentStatus: { not: 'CONFIRMED' } } })`),
which is `catalog-inventory-engineer`'s file — cross-owner, so flagging
rather than silently reassigning. Consistent with this reviewer's
existing "inside a transaction is not serialized" and "ownership checks
split from the mutation statement" learnings.

**A3 — INFO — two small hardening notes.**
(a) `confirmRow:126-130` and `failRow:296-301` re-enter themselves after
a lost CAS with no depth bound. Terminating today because
`PaymentTransaction.status` is monotone (nothing in the repo writes it
back to `PENDING` — verified by grepping every `PaymentTransaction` write
in `src/lib`), but that is a *global* invariant, not a local one; an M4-2
retry/refund feature that reopens a row would turn this into an
unbounded loop holding a webhook request open. A small attempt counter
would make the guarantee local.
(b) `:116` sets `metadata = ${metadata}::jsonb` — a wholesale overwrite,
where ADR Decision 4 specified a jsonb merge. Harmless today (confirmed
by direct read: no code path writes `PaymentTransaction.metadata` before
the webhook — `paymentService.ts:391`'s `metadata` is the *Stripe-side*
session metadata, not the column), and the overwrite is the safer
default for the allowlist invariant. Recorded only so a future writer of
that column knows this statement will silently drop it.

## Red-team notes (attacks attempted on paper, all closed)
- Forge/replay the webhook → HMAC + 300 s tolerance, zero DB touch on
  failure, identical 400 body. No oracle.
- Replay a *valid* captured delivery → dedup rests on durable business
  state (`PaymentTransaction.status` + `Order.paymentStatus`), not on a
  remembered event id, so it survives the crash gap; `onHand` decrement
  is proven once-only sequentially (`:347`) and concurrently (`:374`).
- Point a signed event's `metadata`/`client_reference_id` at another
  customer's order → anomaly throw before any write; and even without
  that guard, every write uses `row.orderId`, never the event's.
- Hit the route logged-out / with a session cookie → irrelevant, no auth
  is consulted and none is needed; there is no second entry point into
  the handler.
- Decline a card mid-session to free stock (`charge.failed`) → routed to
  the `default` branch before any DB call.
- Race `checkout.session.expired` against `completed` → guarded (see A2
  for the residual order-status window).
