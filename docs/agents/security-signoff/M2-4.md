# Security review — M2-4 (Homepage — category cards & search entry point)

STATUS: CLEAR

Read-only pass over src/app/page.tsx, tests/test15-homepage.test.ts,
vitest.config.mts and FEATURES.md M2-4, plus the reused surfaces the diff
depends on (SearchBar.tsx, searchParams.ts, productService.ts:400-449,
region.ts, products/page.tsx:1-70, layout.tsx, tests/setup.ts). Four
advisory findings, none blocking: F1/F2 LOW, F3 LOW (test hygiene), F4 INFO.

## Checked

- PCI scope: checked, no finding. page.tsx and test15 contain no card
  field, no PAN-shaped literal, no Stripe/M-Pesa token or credential, and
  touch no payment module. The only data leaving the DB is
  Product.category strings.
- Payment idempotency: N/A — no webhook handler, no mutation of any kind.
  The homepage is a GET-only Server Component; it issues five read queries
  and returns markup.
- Auth: checked, no finding. No credential field, no custom JWT, no custom
  session table (AHD8 holds). The homepage is deliberately public and
  exposes nothing role-gated — it renders only category names already
  visible to anonymous visitors at /products. No admin route touched.
- Presence-check middleware: checked, no finding. src/middleware.ts is not
  in this diff and its matcher (/profile/:path*) does not cover "/" — the
  homepage neither adds a protected surface nor relies on middleware for
  anything. No forged-cookie test is owed here because there is no
  page-level auth check to prove non-trivial.
- Secrets: checked, no finding. No literal value introduced in any file.
  The only env read is NEXT_PUBLIC_REGION (public by name/prefix) via
  resolveRegion(). Note (positive): InvalidRegionError's message embeds the
  raw misconfigured env value (region.ts:22-24), but page.tsx:54-63 catches
  it and renders a generic static string, never `err.message` — the value
  is not reflected to the visitor and not logged. Test15 reads only
  HOMEPAGE_TEST_PORT.
- Admin audit log: N/A — no admin mutation in this diff.
- Input validation: checked, no finding at runtime. The page takes no
  searchParams and no user input at all; SearchBar is handed
  parseSearchState({}) (a hardcoded empty object literal, not
  request-derived), so every bound in searchParams.ts is trivially
  satisfied. Values rendered are DB-sourced, not client-sourced.
- Data residency: checked, no finding. Region comes from resolveRegion()
  (single-region-per-deployment, per M2-1) and is passed straight to
  getProductFacets, whose price aggregate filters on `region`. No
  cross-region read, no hardcoded region, nothing routed to a region other
  than the deployment's own. run-state.md's eu-west-2 decision is untouched.

## Targeted questions from the dispatch

1. XSS / injection via free-text Product.category — no finding.
   - href: `/products?category=${encodeURIComponent(category)}`
     (page.tsx:94). Not string-concatenated into raw HTML; passed as a
     JSX prop to next/link, so React attribute-escapes it on top of the
     percent-encoding. Because the value is interpolated after a literal
     `/products?category=` prefix, a category named `javascript:alert(1)`
     or `//evil.tld` cannot produce a scheme-changing or protocol-relative
     href — the URL is always same-origin and always path `/products`. No
     open redirect, no SSRF (nothing server-side fetches this value).
   - Link text: `{categoryLabel(category)}` (page.tsx:100) is a JSX text
     child — React escapes it. No dangerouslySetInnerHTML anywhere in the
     file (grepped). A category containing `<script>` renders as inert
     text.
   - Downstream: the `category` param lands in parseSearchState (bounded
     to 100 chars, dropped-not-truncated) and then an exact-match Prisma
     `where` — parameterized, no raw SQL. Already reviewed at M2-2.
   - `q` is never produced by this page (SearchBar builds it client-side
     via URLSearchParams, which encodes).

2. force-dynamic / data-exposure / DoS — see F2. No data-exposure issue:
   getProductFacets filters `isActive: true, deletedAt: null` on Product
   and on ProductVariant, so soft-deleted/inactive rows cannot surface;
   and the page renders only `facets.categories`, discarding brands,
   priceRange and attributes (computed but never emitted into the HTML —
   confirmed by reading the JSX, not assumed). force-dynamic itself is
   correctly justified in-file (a statically prerendered homepage would
   bake in build-time categories and require a live DATABASE_URL at build).
   The cost side is F2.

3. Zero-categories test's deactivate/restore — see F3. The restore logic
   is correct in the happy and thrown-error paths: it captures only rows
   that were already `isActive: true`, so the `finally` restore cannot
   wrongly activate a row that was inactive beforehand, and it targets an
   explicit id list rather than a broad predicate. The gap is crash-safety
   and DB-targeting, not correctness.

4. Standard sweep: no secrets, no new unauthenticated write path (the diff
   adds zero routes, zero Server Actions, zero mutations — the only writes
   in the diff are inside the test file), no SSRF, no open redirect.

## Findings

F1 (LOW) — src/app/page.tsx:29-39, 98. `CATEGORY_ICONS[category] ??
DEFAULT_CATEGORY_ICON` is an unguarded index into an object literal, so
the lookup walks Object.prototype. A Product.category whose literal value
is "constructor", "toString", "valueOf", "hasOwnProperty", "isPrototypeOf"
or "__proto__" resolves to an inherited function/object instead of
undefined, the `??` fallback never fires, and React is handed a
non-renderable child — a broken card at best, a 500 on the site's
highest-traffic public route at worst. Not currently reachable by an
anonymous attacker (Product.category is populated by seed today; the admin
product-create surface is M5 and does not exist yet), which is why this is
LOW rather than MEDIUM — but it becomes admin-input-reachable the moment
M5 lands, and the exclusion of page.tsx from coverage (see F4 rationale)
means no unit test will catch it. Suggested shape: `Object.create(null)`
for the map, a `Map`, or an `Object.hasOwn(CATEGORY_ICONS, category)`
guard. Route to storefront-admin-engineer; ideally fixed now rather than
carried into M5.

F2 (LOW, availability/cost) — src/app/page.tsx:14 + 68. force-dynamic
means every single anonymous homepage hit runs the full getProductFacets
five-query fan-out, of which the page uses exactly one result
(`categories`). The expensive part is
productService.ts:412-415: `productVariant.findMany` selecting
`attributes` for EVERY active variant with no take/limit, followed by an
in-process loop building an attribute map that is then discarded
(page.tsx never reads facets.attributes/brands/priceRange). Cost grows
linearly with catalog size and is paid per request on the most-hit
unauthenticated route, with no rate limiting on page routes (rateLimit.ts
is wired only to /api/cart/add) — a cheap unauthenticated amplification
vector against Postgres, and a real bill at scale. The homepage needs a
single `SELECT DISTINCT category`, not the whole facet payload. Suggested
shape: a narrow `getCategories(region)` in productService, and/or wrap it
in `unstable_cache`/a short `revalidate` instead of force-dynamic (a
minutes-old category list is acceptable; a build-time-frozen one is not,
which is the actual concern the in-file comment argues against). Route to
catalog-inventory-engineer + storefront-admin-engineer. Not blocking M2-4.

F3 (LOW, test hygiene / data integrity) — tests/test15-homepage.test.ts:
144-178. Two issues with mass-mutating real seeded rows:
  (a) Not crash-safe. The `finally` restore does not run if the vitest
      process is killed (Ctrl-C, CI job cancellation, OOM, SIGKILL after a
      hung dev server) mid-`try`. The dev DB is then left with EVERY
      product `isActive: false` — every subsequent test file and any
      running dev server sees an empty catalog, which presents as a
      confusing cascade of unrelated failures rather than an obvious
      "test 15 died." Cheap mitigations: an idempotent re-seed/repair
      step, or an explicit note in the file header naming the recovery
      command.
  (b) No dev-DB guard. tests/setup.ts:20 only fills DATABASE_URL when it
      is not already present, so an ambient exported DATABASE_URL in the
      operator's shell wins over .env.development. This test is the first
      in the suite to issue an unbounded `updateMany` across the entire
      Product table, so that ordinary env-precedence rule now has a
      worst case of deactivating a live catalog. Suggested shape: assert
      the resolved database name matches a dev/test pattern (or that
      NODE_ENV !== "production") before the first updateMany, and fail
      the test loudly if not. Route to qa-dogfood-engineer /
      storefront-admin-engineer.
  Positive, deliberately noted: the restore targets a captured id list of
  rows that were already active, so it cannot activate a row that a human
  had intentionally deactivated. That part is right.

F4 (INFO, not a security finding) — two docs/config notes for the gate:
  - vitest.config.mts:158-167. I checked page.tsx's imports myself rather
    than accepting the stated analogy (per my own standing rule on
    coverage-exclude drift): it imports next/link, a client component that
    calls useRouter, and is an async Server Component, and this repo has
    no RTL/jsdom setup — so "only reachable via a spawned subprocess" is
    genuinely true here, unlike the addressValidation.ts case that
    prompted that rule. The exclusion is legitimate, the pure libs it
    calls (productService/region/searchParams) correctly remain measured,
    and it was moved out of the "scaffold" bucket rather than left there
    dishonestly. No finding. Caveat: F1 lives in exactly the unmeasured
    strip, which is why F1 should be fixed by inspection rather than left
    for a test to catch.
  - vitest.config.mts:40-43 still describes src/app/layout.tsx as
    "create-next-app scaffold ... Will stop being excluded the moment real
    storefront UI lands here (M2+)." Real storefront UI has now landed, and
    src/app/layout.tsx:15-18 still ships `title: "Create Next App"` /
    `description: "Generated by create next app"` — so the visible browser
    tab title of the newly de-scaffolded homepage is still the scaffold's.
    Out of M2-4's literal scope; flagging because M2-4's whole premise is
    "the / route is still the untouched scaffold."
