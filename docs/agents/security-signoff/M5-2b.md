  money-adjacent state transition it does introduce
  (`fulfillmentStatus -> SHIPPED`) is protected by a genuine serialization

  `SELECT id FROM "Order" WHERE id = ${orderId} FOR UPDATE` is verified by

  surface here. Two independent guards (`existingShipments > 0` AND the
  terminal-status check) each independently block a second attempt —
  defense in depth, not a single point.

- **Precondition reorder (specifically scrutinized):**
  1. *Is the builder's reasoning correct?* **Yes, traced independently.**
     Step (e) (`:135`) sets `fulfillmentStatus: "SHIPPED"` in the same
     transaction that creates the `Shipment` row, and `"SHIPPED"` is the
     first member of `TERMINAL_FULFILLMENT` (`:20-26`). A repo-wide grep
     confirms `markOrderShipped()` is the **only** `Shipment` writer in
     `src/`, so a `Shipment` row can only ever coexist with
     `fulfillmentStatus === "SHIPPED"`. Under the ADR's literal order
     (terminal check before shipment-count check), `OrderAlreadyShippedError`
     is therefore structurally unreachable and tests 17/18's required
     `ALREADY_SHIPPED` outcome would be impossible. The deviation is
     justified, and it is flagged in-code at `:94-109` rather than made
     silently.
  2. *Does the reorder preserve every other precondition?* **Yes.** The
     three guards form a pure conjunction with no side effects between
     them (zero writes occur before `:120`), so the set of inputs that
     reaches the write block is order-independent: `paymentStatus ===
     "CONFIRMED"` AND `existingShipments === 0` AND `fulfillmentStatus ∉
     TERMINAL`. No new bypass is possible. Specifically checked:
     *CANCELLED-without-a-shipment* still falls through the shipment
     check (count 0) into the terminal check and yields
     `FULFILLMENT_TERMINAL` (`:116-118`), proven by test 16 and by the
     in-process precondition test asserting
     `rejects.toBeInstanceOf(OrderNotShippableError)` with zero rows;
     *PAYMENT_NOT_CONFIRMED* is unaffected because it remains **first**
     (`:110`) — an unpaid order is still refused before either of the
     reordered checks, proven by tests 14/15. No new unreachable path is
     introduced: `FULFILLMENT_TERMINAL` remains reachable via the
     CANCELLED-no-shipment case.
  3. *Does the regression test still prove what it claims?* **Yes.**
     Tests 17 and 18 assert `body.code === "ALREADY_SHIPPED"` (not merely
     "409"), so restoring the ADR's literal order turns them red
     (`FULFILLMENT_TERMINAL`), and deleting the `existingShipments` check
     also turns them red for the same reason — the assertion pins the
     deviation rather than tolerating it. Test 18's lock non-triviality
     (two `Promise.all` POSTs, asserting `[200, 409]` and exactly one row
     in each of the three tables) is also structurally sound under the
     reorder: without the lock, both transactions read `count === 0` and
     both insert, producing 2 shipments and failing the assertion.

## Advisories (non-blocking, recorded for follow-up)

- **A1 (LOW-MEDIUM) — the audit log's `ipAddress` is derived from a
  client-settable header, and this is the first item where that matters.**
  `ship/route.ts:112` uses
  `headers().get("x-forwarded-for")?.split(",")[0]` — M5-2a's documented
  convention, correctly never used for authorization. But `AdminAuditLog`
  exists as an insider-accountability control (AHD7), and the acting
  admin can set `x-forwarded-for` themselves, so the one forensic field
  that attributes *where* an action came from is spoofable by exactly the
  actor it is meant to record. Same class as this reviewer's M4-2
  "client-settable headers as a rate-limit key" entry. Recommend a
  platform-set header (`x-vercel-forwarded-for`) with `x-forwarded-for`
  as a dev-only fallback, done once in a shared helper so M5-2c/d inherit
  it. Not blocking: the field is forensic only and no decision reads it.

- **A2 (LOW) — `trackingUrl` is stored raw rather than normalized.**
  `ship/route.ts:79` assigns `trackingUrl = trackingUrlRaw`, not
  `parsed.href`, so the value persisted is not byte-identical to the
  value validated (embedded tab/CR/LF are stripped by the parser but
  survive into the DB). I could construct no scheme-confusion exploit —
  HTML `href` parsing strips the same characters, and the divergence is
  in the fail-safe direction — so this is defense in depth, not a live
  bug. Storing `parsed.href` makes "what was validated" and "what is
  rendered at `[orderId]/page.tsx:195`" the same string.

- **A3 (LOW) — no forged-cookie test targets the two new `(secure)`
  pages, and M5-2a's "second admin route" test does not actually cover a
  second route.** `tests/test28-admin-rbac-2fa.test.ts:403-421` is titled
  "the forged-cookie rejection also holds on a second admin route under
  the same (secure) layout" but fetches `${BASE_URL}/admin` (`:409`) —
  the same URL as the preceding test — so no page inside the `(secure)`
  group has a forged-cookie proof today. M5-2b now adds two such pages.
  The property holds structurally (both pages call `requireAdmin()` as
  their first statement, `orders/page.tsx:46` and
  `orders/[orderId]/page.tsx:17`, and I read both), and the *mutation*
  route is fully proven by test 1 because middleware does not cover
  `/api/admin/*` at all. But per this repo's own standing rule, a cheap
  addition to test29 — garbage value under the runtime-derived
  `session_token` cookie name against `/admin/orders`, asserting the
  `?reason=admin_no_session` marker — would make the page-level gate
  falsifiable rather than argued. Recommend fixing test28:409's URL at
  the same time.

- **A4 (LOW) — first cookie-authenticated admin state-changing POST, with
  no origin/CSRF check.** `POST /api/admin/orders/[orderId]/ship` is
  authenticated purely by the session cookie; `request.json()` parses the
  body regardless of `Content-Type`, so the classic `enctype=text/plain`
  cross-site form trick is not blocked at the parser. Protection today
  rests entirely on better-auth's **default** `SameSite=Lax` — `auth.ts`
  sets no `advanced.cookies`/`sameSite` config, so this is an external
  library invariant, not a local guarantee (my "prefer cannot leak over
  does not leak" rule). Consistent with every pre-existing POST route in
  this repo, so not introduced here — but the blast radius is now an
  admin mutation. Recommend an explicit `Origin`/`Sec-Fetch-Site` check
  in a shared admin-route helper, or pinning the cookie policy
  explicitly, owned by whoever lands M5-2c.

- **A5 (INFO) — precondition-reorder side effect, deliberate and safe.**
  An order that is terminal **and** has a shipment (reachable only via
  ship-then-cancel, which has no writer today) now reports
  `ALREADY_SHIPPED` rather than `FULFILLMENT_TERMINAL`. Both are 409 with
  zero writes, so this is a diagnosis-string change, not a control
  change. Worth remembering if a future item adds a cancel-after-ship
  path and ops keys on the code.

- **A6 (INFO) — two standing repo-wide gaps restated so they are not lost
  at the gate.** (i) Validation is hand-rolled, not Zod as the PRD's
  Definition of Done words it; this follows the established
  `addressValidation.ts` convention and the repo carries no `zod`
  dependency — a repo-level decision, not something introduced here.
  (ii) Denied mutation attempts (403 VIEW_ONLY, 409 preconditions) write
  no `AdminAuditLog` row and no other trace, so repeated attempts by a
  VIEW_ONLY admin are invisible. That is consistent with AHD7's wording
  ("every admin *mutation*"), but a denied-attempt trail is the kind of
  thing an ops/security review will ask for later.
