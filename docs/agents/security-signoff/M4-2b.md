## Fix-by-fix re-verification

### F1 (HIGH) — FIXED, and the fix closes the exact gap I found

The three shared helpers exist at `mpesaCallbackService.ts:369-433`:
`findOtherConfirmedTransaction` (`:369-377`), `writeDoublePaymentEvent`
(`:379-403`), `detectAndFlagDoublePayment` (`:416-433`).

`findOtherConfirmedTransaction` is the right predicate, checked field by
field: `{ orderId, id: { not: excludeId }, status: "CONFIRMED" }` — scoped to
the order, excluding self, and **provider-agnostic** (no `provider` clause),
which is the whole point. It is deliberately *not* provider-scoped, matching
my learnings entry's rule that the "is anyone else already paid" question must
stay global while row *mutation* stays provider-scoped.

I traced the exact F1 sequence again against the current code. Step 6 now
reads: `enterConfirmSwitch` `case "PENDING"` → `casPendingToConfirmed`
succeeds (`:469-470`) → **`detectAndFlagDoublePayment` at `:476-477`, before
`runConfirm`** → finds the CONFIRMED stripe row → writes
`PAYMENT_DOUBLE_PAYMENT_DETECTED` with `refundRequired: true` → returns
`{ outcome: "double_payment_flagged" }`. The silent `"duplicate"` return is
gone from that path. Critically the check runs **before**
`confirmReservationsForOrder`, so the double payment is detected on its own
terms rather than being inferred from a thrown
`ReservationNotActiveError` — which also means it is still detected on an
order with zero reservations, where that error would never have thrown.

Reachability from every status a late `ResultCode: 0` can land on — I
enumerated the switch rather than trusting the comment:

- `PENDING` → checked at `:476` on CAS success; on a lost CAS the code
  refetches and re-enters the switch (`:482-483`), so it lands on one of the
  arms below rather than falling through.
- `CONFIRMED` (crash-gap resume) → checked at `:512-513`, after the
  already-flagged short-circuits and before `runConfirm`.
- `FAILED` / `CANCELLED` → `lateSuccess`, which no longer carries its own
  inline copy: `:761-762` calls the same shared
  `detectAndFlagDoublePayment`. I confirmed by reading the whole function
  that the old inline `otherConfirmed` query and its bespoke event write are
  gone — there is exactly one `findFirst` for a CONFIRMED sibling in the file
  (`:373`) and exactly one `PAYMENT_DOUBLE_PAYMENT_DETECTED` create (`:384`).
- `INITIATED` / unknown → throw, no write. Correct.
- Plus the race-window net inside `runConfirm`'s
  `ReservationNotActiveError` / `err.status === "CONFIRMED"` catch
  (`:559-568`), which runs the same check before falling back to the
  "concurrent sibling of my own confirm" interpretation. This is real defense
  in depth, not a duplicate of the pre-check: it covers a competing confirm
  committing *between* the pre-check and the reservation call.

Idempotency of the new event: `detectAndFlagDoublePayment` guards the write
with `findEvent(orderId, "PAYMENT_DOUBLE_PAYMENT_DETECTED", row.id,
"lateePaymentTransactionId")` (`:423-431`) and returns the flagged outcome
either way, so a redelivery writes no second event but still reports the
non-benign outcome. The `payloadKey` override is necessary and correct — the
payload keys this event on `lateePaymentTransactionId`, not the default
`paymentTransactionId`, and passing the default would have made the guard
never match and duplicated the event on every redelivery. Verified the two
`findEvent` call sites that look for this event type (`:423`, `:496`) both
pass the override; the `PAYMENT_CONFIRMED_STOCK_UNAVAILABLE` /
`PAYMENT_AMOUNT_MISMATCH` lookups correctly keep the default. No stock is
decremented on the flagged path because `confirmReservationsForOrder` is
never reached.

The new regression test (`tests/test24-mpesa-callback.test.ts:1167-1246`) is
non-trivial, and I checked that by reasoning over the code rather than taking
the claim: it seeds row A as `PENDING` (`:1181`, `createPendingMpesaRow`) —
not `FAILED` as test 26 does — with row B `CONFIRMED` under `it.each(["mpesa",
"stripe"])` and the order/reservations/inventory already advanced to simulate
the prior confirm (`:1197-1202`). With `:476-477` removed, that fixture walks
CAS-success → `runConfirm` → `ReservationNotActiveError('CONFIRMED')` →
`order.paymentStatus === 'CONFIRMED'` → `{ outcome: "duplicate" }`, so
`:1211` fails exactly as `expected 'duplicate' to be
'double_payment_flagged'`. The builder's reported failure string is the one
the code actually produces — consistent with the claimed revert-and-rerun.
The test also asserts the payload shape including `refundRequired: true`
(`:1219-1224`), a single event on redelivery (`:1240-1243`), and — the
assertion that makes it a money-path test rather than a string test — that
`onHand` equals the post-prior-confirm value, i.e. decremented exactly once
in total (`:1229-1231`).

### F2 (MEDIUM) — FIXED, with no gap reopened

`.env.development:38` is now `MPESA_CALLBACK_SECRET="REPLACE_ME"`, matching
every sibling M-Pesa credential in the same block (`:21-24`) and
`.env.example:68`. The old in-file justification is replaced by `:29-37`,
which now states the opposite and correct thing — that a real value here is
the entire trust boundary the moment the tunnel workflow documented three
lines above is used.

I checked each way this fix could have reopened something:

- **Production untouched, correctly.** `.env.production.kenya` still names
  `MPESA_CALLBACK_SECRET` only in a comment (`:16`, "set in Vercel as
  encrypted") and holds no value; `MPESA_CALLBACK_URL` at `:13` is unchanged
  and still byte-consistent with `.env.example:61` / `.env.development:28` and
  `docs/DEPLOYMENT.md`. The M4-2 "fix scoped to files I touched" class has not
  recurred in either direction — nothing needed changing there and nothing
  was.
- **The generated test secret is never persisted.** `tests/setup.ts:42-48`
  assigns `process.env.MPESA_CALLBACK_SECRET = randomBytes(32).toString("hex")`
  and nothing else: no `writeFileSync`, no `appendFile`, no `fs` write of any
  kind in the file (its only `node:fs` imports are `readFileSync`/`existsSync`,
  `:13`, used solely by `loadDotEnv`). The value is process-scoped and dies
  with the run. It is not logged.
- **The guards it exercises are not weakened.** The trigger condition
  (`unset || === "REPLACE_ME" || length < 32`) generates a *stronger* value
  rather than lowering either threshold — `buildCallbackUrl`'s outbound
  `< 32` / `REPLACE_ME` rejection and `verifyMpesaCallbackToken`'s inbound
  fail-closed check (`mpesa.ts:314-322`, re-read, unchanged) are both intact
  and still tested against the placeholder explicitly
  (`tests/test24:467-471` sets `REPLACE_ME` and asserts it is rejected
  identically to unset).
- **Precedence is right.** The generation runs *after* `loadDotEnv`, and
  `loadDotEnv` only fills unset vars, so a developer's real `.env.local` value
  (or a CI-injected one) still wins. A real 64-hex dev value in `.env.local`
  is >= 32 and not `REPLACE_ME`, so it is not clobbered.
- **Burn status.** M4-2b is still uncommitted work (the callback files are
  untracked and `.env.development` shows as modified-not-committed), so the
  previously-live value existed only in the working tree and did not enter git
  history. It should nonetheless never be reused for any tunnel; the fix as
  built makes that easy since no value is committed at all now.

### F4 (LOW) — FIXED, and I swept for the same pattern elsewhere

`mpesa.ts:410-416` now gates the coercion on
`typeof raw.ResultCode === "number" || (typeof raw.ResultCode === "string" &&
raw.ResultCode.trim() !== "")` before the `Number.isNaN` check. I walked the
falsy set by hand against this predicate: `""` → string, trims to `""` →
rejected; `" "` → rejected; `false`, `[]`, `[0]`, `{}`, `null`, `undefined` →
not number, not string → rejected. `0` and `"0"` still pass (test 29's
string-form support preserved), and `"abc"` passes the shape gate but is
caught by `Number.isNaN`. The only residue is a numeric `Infinity`, which is
`typeof "number"` and not `NaN` so it parses — but it is not `0`, so it routes
to the fail path, which is the safe direction. Airtight for the
success-sentinel concern.

Sibling sweep (my learnings' "a fix scoped to the files I touched" rule): I
grepped every `Number(` / `parseInt` / `parseFloat` under `src/` and read the
three that could matter.
`mpesa.ts:152` (`Number(body.expires_in)`) is guarded by
`Number.isFinite && > 0` and falls back to *immediate expiry* — the fail-safe
direction, no cached token with a garbage lifetime.
`productService.ts:207-211` guards with `!raw` then `Number.isFinite && >= 0`
before constructing a `Decimal`, and its sentinel is a price filter, not a
success code. `mpesaService.ts:469` coerces from an already-validated
`Decimal.toFixed(0)`. The remaining hits are display formatting in components
and `cartView`/`reservationService` arithmetic on `Decimal`-derived values, no
sentinel comparison. No other instance of this class exists on the money path.

### F6 (LOW) — FIXED, and it is not a bypass

`assertRowIdentity` (`mpesaCallbackService.ts:167`) now includes
`&& cb.merchantRequestId !== ""` in the guard, so an omitted
`MerchantRequestID` (which `parseStkCallback:402` defaults to `""`) skips the
comparison instead of throwing forever.

Red-teaming the "deliberately omit it to dodge the check" question: it grants
an attacker nothing. To reach `assertRowIdentity` at all you must already hold
the URL secret *and* a valid `checkoutRequestId` — and with those, the
`merchantRequestId` check was never an obstacle, because `MerchantRequestID`
is not a secret or an authorization factor; it is a correlation id that any
party holding the envelope already knows, and a hostile caller could simply
send the matching value. The assertion's real purpose is detecting Daraja-side
identity confusion (two ids that disagree), not authenticating the caller.
Nothing else is skipped: the `provider !== "mpesa"` check above it (`:153`)
still runs unconditionally, row resolution is still an exact `findUnique` on
the `@unique` `providerTxId` (`:135-138`), and the amount reconciliation
(`:450-456`) still runs before any confirm. The skip is also the same
already-accepted shape used when `row.metadata` is null. No bypass.

### F3 (LOW, partial) — accept as a documented non-blocking follow-up

Caps landed where it matters: `checkoutRequestId` is rejected as malformed
above 256 chars at parse time (`mpesa.ts:394-400`), which is the one that
actually mattered because it is a `@unique` btree key whose insert failure
would 500 and trigger indefinite Daraja redelivery; `resultDesc` is capped at
500 **at the source** (`mpesa.ts:422`) so every downstream consumer inherits
the bound rather than each write site having to remember; and `rawPayload` is
bounded at 64 KiB by `boundRawPayload` (`mpesaCallbackService.ts:216-237`),
which on overflow stores a structured `{ truncated, reason, originalByteLength,
preview }` marker rather than dropping the evidence. I checked its failure
modes: a circular/unserializable body is caught and stored as a marker rather
than throwing (`:220-224`), and `JSON.stringify(...) ?? "null"` handles
`undefined`. Minor note, not a finding: the constant is named `…_MAX_BYTES`
but `serialized.length` counts UTF-16 code units, so a fully multi-byte
payload could reach a few hundred KiB — still bounded, still fine.

The 3 s orphan-resolve sleep (`ORPHAN_RESOLVE_ATTEMPTS` × 1 s, `:78-79`,
`:197-204`) is unchanged. I agree this is acceptable to leave as a LOW
advisory: it is reachable only with the URL secret, only on an *unmatched*
`ResultCode: 0`, it exists to close a real money-path race (the Phase-C
`providerTxId` write), and shortening it trades a correctness guarantee for an
availability margin — exactly the kind of call that belongs in the ADR
(Decision 4) rather than in a security fix. Worth revisiting alongside
platform-level rate limiting on the webhook path, not here.

### F5 (LOW, deferred) — comfortable leaving non-blocking

Unchanged at `mpesaCallbackService.ts:505-506` vs `:684-691`. My original
assessment holds: it requires the bearer token plus a live
`CheckoutRequestID`, it matches the ADR's Decision 5 spec exactly (so it is an
ADR-level design gap, not a build defect), and its failure mode leaves the
money durably recorded (`PaymentTransaction` CONFIRMED plus a
`PAYMENT_AMOUNT_MISMATCH` event) rather than losing it — an ops-visible stuck
order, not a silent one. Correctly routed to platform-architect/human as a
design question. Non-blocking.

## Non-blocking advisories carried forward

### F3 — LOW (partially addressed) — orphan-resolve forced sleep retained
See above. Size caps landed; the 3 s (`3 × ORPHAN_RESOLVE_DELAY_MS`) held
invocation per unmatched `ResultCode: 0` is retained per ADR Decision 4.
Owner: platform-architect, alongside webhook-path rate limiting. Note the ADR
prose still estimates "~2 s" where the code does 3 s — worth correcting when
that section is next touched.

### F5 — LOW (deferred by design) — `PAYMENT_AMOUNT_MISMATCH` latches out a later crash-gap resume
`mpesaCallbackService.ts:505-506` vs `:684-691`. Unchanged; routed to
platform-architect/human as an ADR-level question. See above.

### F7 — NEW, LOW — a crash between the PENDING CAS and the double-payment event write loses the ops signal permanently
`src/lib/mpesaCallbackService.ts:469-478` and `:489-495`. The F1 fix's CAS
(`casPendingToConfirmed`) and its `PAYMENT_DOUBLE_PAYMENT_DETECTED` write are
two separate statements, not one atom. If the process dies in between, the
redelivery enters `case "CONFIRMED"` and returns `{ outcome: "duplicate" }` at
`:493-495` — the `order.paymentStatus === "CONFIRMED"` early return sits
*above* the `detectAndFlagDoublePayment` call at `:512`, so the event is never
written. The window is milliseconds and the durable evidence survives (two
CONFIRMED `PaymentTransaction` rows on one order remain queryable, and the
M4-2c reconciliation job is the right place to catch that), so this is a
strictly narrower residual than F1 was, not a reintroduction of it.
**Suggested fix (non-blocking):** move `detectAndFlagDoublePayment` above the
`order.paymentStatus === "CONFIRMED"` early return in the `CONFIRMED` arm — it
is already idempotent, so running it first costs one indexed query on the
redelivery path and closes the gap. Owner: commerce-payments-engineer,
whenever this file is next opened.

### F8 — NEW, LOW — an amount-mismatched late callback on an order another provider already paid gets no double-payment event
`src/lib/mpesaCallbackService.ts:454-455`. Decision 5's amount reconciliation
runs *before* the confirm switch and takes its own terminal branch
(`amountMismatch`), which never calls `detectAndFlagDoublePayment`. So the
combination "another provider already CONFIRMED this order" **and** "the late
M-Pesa amount doesn't match" produces `PAYMENT_AMOUNT_MISMATCH` but no
`PAYMENT_DOUBLE_PAYMENT_DETECTED`, and the ops double-payment queue misses it.
This is materially less severe than F1 was — a loud, refund-implying event
*is* written and the row is left CONFIRMED (so `assertNoBlockingAttempt` still
blocks a third charge) — so nothing is silent; the signal is just filed under
the wrong queue. **Suggested fix (non-blocking):** call
`detectAndFlagDoublePayment` on the mismatch branch too, writing both events
(they answer different ops questions). Owner: commerce-payments-engineer.
