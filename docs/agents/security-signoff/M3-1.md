## First-pass findings — disposition

### F1 (HIGH) — session fixation on logout — CLOSED
- Hook fires: better-auth registers the endpoint as
  `createAuthEndpoint("/sign-out", ...)` (sign-out.mjs:15) and dispatch.mjs:199
  sets `path: endpoint.path` on the hook context, so `ctx.path === "/sign-out"`
  (src/lib/auth.ts:104) matches. getHooks (dispatch.mjs:147-154) registers a
  user-level `hooks.after` with `matcher: () => true` — it is reached.
- Rotation is real: cartCookie.ts:75-79 mints a fresh `randomUUID()` and writes
  it via setCartSessionId; it is not a re-issue of the same value.
- Test is non-trivial (tests/test14-cart-api.test.ts:864-930): real sign-up →
  real sign-in → authenticated add (cart bound to userId, cookie C1) →
  sign-out carrying both cookies → asserts C2 exists, C2 != C1, and that a
  subsequent GET /api/cart with C2 returns `cart.id === null` and `items: []`.
  It proves the rotated cookie cannot reach the logged-out user's cart, which
  is the correct assertion for the cookie-continuity threat model.
- Residual, tracked as F8/F9 below: the old row keeps both its old sessionId
  and its userId, so possession of the pre-rotation value still grants access.

### F2 (HIGH) — claim path seizing another user's cart — CLOSED
cartService.ts:378-392. Two guards now:
- `winner.userId !== null && winner.userId !== userId` → `return
  getOrCreateCart({ userId, region })`, recursing WITHOUT the planted
  sessionId. That call resolves the requester's own cart by userId if one
  exists, else mints a fresh UUID and a new row; the route then overwrites the
  planted cookie via setCartSessionId. Correct fallback — creates a new cart
  for the requester, neither errors nor silently no-ops. Terminates.
- Claim is now `userId && winner.userId === null` — only ever an unowned row.
All four combinations traced (own cart / other user's cart / guest-vs-guest
race / guest requester hitting an owned row); none returns or reassigns
another user's row. No dedicated regression test for the "different real
user" branch — noted, not blocking, since the branch is reachable only via a
planted cookie plus a lost P2002 race.

### F3 (MEDIUM) — sessionId echoed in response body — CLOSED
add/route.ts:83-99 returns `{ cart, cartId }` only; the removal is documented
in-place with a do-not-re-add note. Grep across src/app/api/cart confirms no
other route emits it. Tests assert `body.sessionId === undefined` AND
`JSON.stringify(body)` does not contain "sessionId", on both the new-cart
(:756-757) and existing-cart (:784) paths.

### F4 (MEDIUM) — no rate limit — ADEQUATE, documented stopgap
- Enforced: add/route.ts:32-39, 30 req / 60s keyed per-IP, returns 429 with a
  `Retry-After` header in seconds. Scoped to /api/cart/add only, which is
  correct — it is the sole row-minting route.
- Tested (:934-977): loops until a real 429, asserts Retry-After present and a
  non-empty error body, then asserts an immediate follow-up is ALSO 429 —
  proves the window persists rather than a one-off.
- Known limit is documented, not hidden: rateLimit.ts:10-16 states plainly
  that the Map is per-process and that a multi-instance/serverless deploy gets
  `limit` per instance, with the real fix (shared store) named.
- Accuracy/robustness caveats recorded as F10/F11 below.

### F5 (LOW) — cumulative MAX_CART_QUANTITY — CLOSED
cartService.ts:442-450 now checks `newQuantity > MAX_CART_QUANTITY` on the
cumulative total, matching updateCartItemQuantity's bound.

### F6 (LOW) — ids reflected in error bodies — CLOSED
cartService.ts:93-118 logs the id-bearing message server-side and returns
static generic strings; asserted at tests:104-139 including explicit
not-to-contain checks on the id.

### F7 (LOW, repo-wide) — unchanged, still deferred to M6 hardening.

## New residual findings this pass — none blocking M3-1

F8 (MEDIUM) — src/lib/cartService.ts:294-299. `findActiveCart`'s sessionId
branch does not require `userId: null`, so a bare cart cookie resolves a cart
that is already bound to a real user. This lookup runs at getOrCreateCart:335
BEFORE the F2 guard, so F2's protection covers only the P2002 claim path, not
the primary lookup: a holder of a leaked/copied hurbad_cart value can read
(GET /api/cart) and mutate (/api/cart/add) a user-owned cart. Requires
possession of a 122-bit httpOnly value, and today's cart carries no PII, so
not blocking M3-1. MUST be closed before M3-2/M3-3 attach guest email +
shipping address to the cart (ADR Decision 3). Suggested shape: add
`userId: null` to that where clause.

F9 (MEDIUM) — login-side rotation still unwired, so the P2002 claim path is
de-facto promotion-on-login: a planted guest cookie becomes bound to the
victim's account on their first authenticated add (findActiveCart by userId
ignores sessionId → create → P2002 → winner.userId === null → claimed), and
the planter retains a working handle via F8. The first review offered "wire
rotation into login/logout OR gate the claim path off"; only the logout half
was done. Accepted for M3-1 because merge-on-login is explicitly out of scope
(FEATURES.md:696). Suggested shape: when the claim path takes an unowned row
for a user, rotate that row's sessionId and re-issue the cookie.

F10 (MEDIUM) — src/lib/rateLimit.ts:81-82. The key trusts the FIRST
x-forwarded-for entry, which the client controls whenever the proxy appends
rather than replaces. That both bypasses the limit and lets an attacker mint
unbounded distinct `buckets` keys within one window (sweep runs at most once
per windowMs) — a memory-growth vector introduced by the mitigation for a
row-growth vector. Prefer a platform-provided header, or the last XFF entry.

F11 (LOW) — src/lib/rateLimit.ts:1 calls this "sliding-window"; the
implementation is a fixed window (resetAt pinned at the first request), as
the checkRateLimit docstring itself concedes at line 42. Fixed windows admit
~2x limit across a boundary. Fix the comment or the algorithm.

F12 (LOW, doc accuracy, gate-relevant) — FEATURES.md:696 still asserts
rotateCartSessionId is "deliberately not wired into any better-auth
login/logout hook." src/lib/auth.ts:102-108 now wires it into logout. Correct
the ledger before the gate treats it as accurate.

F13 (LOW) — src/lib/cartService.ts:101 logs the caller-supplied variantId
verbatim through console.error; unsanitized newlines permit log-line forging.
No secret or PII involved.

## Iron rules — all checked this pass

- PCI scope: checked, no finding. None of auth.ts, cartCookie.ts,
  cartService.ts, rateLimit.ts, add/route.ts or the tests references card
  data, a PAN-shaped literal, a Stripe token, or an M-Pesa credential.
- Payment idempotency: N/A — no webhook handler in this diff. Noted for M3-2:
  rateLimit.ts's in-memory Map must NOT be reused as a webhook idempotency
  store; per-instance memory cannot make a replayed webhook safe.
- Auth: checked, no finding. `hooks.after` + `createAuthMiddleware` are
  documented better-auth config surfaces, not a hand-rolled session or JWT;
  no credential field, no custom session table added (AHD8 holds). The hook
  only rotates an unrelated cookie and never returns a response, so it cannot
  alter the sign-out result. Every cart route independently calls
  auth.api.getSession() (route.ts:30, add:64, update:41, remove:38).
- Presence-check middleware: checked, no finding. middleware.ts is unchanged
  in this diff and its matcher remains /profile/:path* — no cart route relies
  on it. The F1 test signs in for real rather than hand-crafting a cookie,
  consistent with the forged-value discipline in this repo's learnings.
- Secrets: checked, no finding. No literal value introduced anywhere; the
  rate limiter logs nothing; the new server-side console.error lines carry an
  internal cart id / caller variantId (F13) but no secret, token, or PII.
- Admin audit log: N/A — no admin mutation in this diff.
- Input validation: still server-side and still hand-rolled but correct;
  rate-limit bounds are module constants, not client input. F7 unchanged.
- Data residency: checked, no finding. Region resolution is untouched by this
  diff; carts remain scoped to their own region for price/stock reads.
