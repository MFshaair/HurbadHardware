## Checked

- **PCI scope:** checked, no finding. Neither new page imports Stripe,
  M-Pesa, `paymentService`, `PaymentTransaction`, or any card/token
  module. The analytics page's only money source is
  `DailySalesMetric.revenue` (an aggregate `Decimal(14,2)` column, no
  instrument data); the inventory page reads no money field at all —
  `RegionalPrice` is deliberately not joined
  (`inventory/page.tsx:75-87`). No card data is handled, logged or stored
  on any path in this diff.

- **Payment idempotency:** checked, not applicable, and verified so
  rather than assumed. This diff contains **no webhook handler, no
  mutation of any business table, and no new API route**. The only write
  either page causes is `adminSessionActivity.upsert` inside the
  pre-existing `requireAdmin()` (`adminAuth.ts:154-158`), which is
  idempotent by construction (upsert on `sessionId`). No stock decrement,
  no order confirmation, no reservation transition exists here — so the
  four-transition and idempotency-key rules have no applicable write
  path. Test 7 pins this positively: `Order`/`Shipment`/`OrderEvent`/
  `AdminAuditLog`/`RegionalInventory`/`DailySalesMetric` counts are
  snapshotted before and after driving all three roles through both
  pages and asserted `toEqual`, while `AdminSessionActivity.lastActivityAt`
  is asserted to have advanced (so the assertion is scoped, not a false
  "zero writes" claim). Test 33 additionally greps `src/` for any
  `dailySalesMetric.create|update|upsert|createMany` and asserts the empty
  string, and asserts no new `src/app/api/cron/` entry and exactly two
  `vercel.json` cron paths — i.e. the item genuinely did not silently
  invent the deferred aggregation job.

- **Auth (hand-rolled credentials / independent server-side role
  verification):** checked, no finding. No credential field, no custom
  JWT, no custom session table is introduced — the diff adds zero auth
  code and reuses better-auth via `requireAdmin()`.
  `analytics/page.tsx:146` and `inventory/page.tsx:50` each call
  `await requireAdmin()` as the **first statement of the component**,
  before `await searchParams` and before any DB access — the `(secure)`
  layout is not relied upon as the boundary (ADR Decision 3, M5-2a
  Decision 1/2). Read `adminAuth.ts` in full to confirm the gate it
  provides is unchanged and still real: fresh DB read of `role` (never
  `session.user.role`), allowlist not a `!== "CUSTOMER"` negation,
  `notFound()` rather than 403 for a non-admin, 2FA-enrolment check, idle
  window with session-row revocation.
  **All three admin roles are admitted identically** — neither page
  contains any `role ===` / `VIEW_ONLY` branch (grep-confirmed by reading
  both files in full), so no accidental over-restriction was introduced;
  test 5 drives `ADMIN`/`OPERATOR`/`VIEW_ONLY` through both pages and
  asserts 200 + the same rendered testids, which is the assertion that
  goes red if someone adds a restriction.
  Test 6 confirms neither page renders a mutating control (no
  `method="post"`).

- **Presence-check middleware is never the real gate:** checked, no
  finding — and this is the strongest instance of the pattern in the repo
  so far. Test 1 asserts two *different* outcomes: no-cookie → `307` to
  `/auth/login` (middleware's presence check), and a **forged value under
  the real cookie name** → `307` to `/auth/login?reason=admin_no_session`.
  The cookie name is derived at runtime from a live sign-in response and
  selected **by name match** (`.split("=")[0].includes("session_token")`),
  not positionally — this satisfies the stronger derivation my M5-1b
  learning requires, so the test cannot silently degrade into the
  no-cookie path. Non-triviality is structural rather than empirical: the
  `?reason=admin_no_session` marker is emitted only from
  `requireAdminRole()` (`adminAuth.ts:71,80`), so deleting the page-level
  `requireAdmin()` call would change the observed outcome and turn the
  test red. Both pages are exercised in the loop (not one URL reused
  twice — checked the actual fetch targets, per my M5-2b learning about
  misleading test titles).

- **Secrets:** checked, no finding. No new env var, no new tracked config
  file, no `.env*` change in this diff. Nothing in either page logs
  anything at all (no `console.*` in either new file). The only value the

  `(secure)/page.tsx` and `orders/page.tsx` pattern. The test file's

  test-created-and-deleted users (identical to test28/test29's
  convention), not a real credential.

- **Admin audit log:** checked, correct to omit. This surface performs
  **no admin mutation**, so there is nothing that should be audited and
  isn't — I enumerated every write reachable from both pages and the only
  one is the `AdminSessionActivity` sliding-window upsert. That matches
  ADR Decision 3 and FEATURES.md's M5-2e note. Test 7 asserts

  — correctly scoped to the admins the test created rather than a

- **Injection / input validation:** checked, no finding. This is the
  headline risk of the item and I read the query construction rather than
  the ADR's description of it.
  - `inventory/page.tsx:66-71` builds the shared predicate with
    `Prisma.sql` tagged-template interpolation:
    `` WHERE ri.region = ${region}::"Region" AND (ri."onHand" - ri.reserved - ri."safetyBuffer") < ${LOW_STOCK_THRESHOLD} ``.
    Both `${region}` and `${LOW_STOCK_THRESHOLD}` are **template
    substitution values, not string concatenation** — they become genuine
    bound parameters (`$1`, `$2`), and the `::"Region"` cast is applied to
    the *placeholder*, not to interpolated text. `LIMIT ${LOW_STOCK_LIMIT}`
    (`:90`) is likewise a bound parameter. There is no
    `Prisma.raw(...)`, no `+` concatenation, and no backtick-interpolated
    identifier anywhere in either file. The `Prisma.sql` fragment is
    reused (not retyped) by both the rows query and the count query
    (`:88`, `:97`) per Decision 5's mitigation 1; nesting a `Sql` inside a
    tagged template splices strings **and** re-indexes values, and the
    fragment object is not mutated by either use — so the two statements
    each carry their own correctly-numbered parameter list. Defence in
    depth is present too: `resolveRegion()` (`:26-34`) allowlists the
    value against `Object.values(Region)` and falls back to `KE`, so a
    hostile string never reaches the driver at all. Test 30 fires
    `KE'; DROP TABLE "Product";--` and asserts 200 plus unchanged
    `Product.count()`.
  - Analytics uses no raw SQL: a single bounded `findMany`
    (`analytics/page.tsx:155-159`). `region` is allowlisted to `["KE"]`
    and spread conditionally (`...(region ? { region } : {})`), so
    Prisma's where-undefined footgun (my M5-1b learning) cannot silently
    drop a filter. `from`/`to` are strict-regex-gated and converted to
    `Date` objects before reaching the query, never strings.
  - Result-set bounds are real: the 366-day clamp (`:71-77`) is the only
    bound on the unpaginated analytics query and it is present and
    correct (both endpoints are UTC midnights, so no DST drift in the
    `Math.floor` span); the inventory query carries `LIMIT 200` plus a
    separate count with an honest truncation notice.
  - Untrusted `topProducts` (`parseTopProducts`, `:98-121`): returns `[]`
    for any non-array; per element rejects non-objects, arrays and
    `null`; requires `variantId`/`sku`/`name` to be non-empty strings and
    `qty` to be a finite non-negative integer; wraps the `Decimal`
    coercion in `try/catch`. Every rejection path is `continue` — **there
    is no throw anywhere in the function**, so a malformed blob drops the
    element and cannot 500 the dashboard. Walked the hostile inputs by
    hand: `{}` → `[]`; `[{}]` → dropped; `[null]`, `[[]]` → dropped;
    `revenue` absent/`null`/`true`/object/`[]` → `String(...)` yields
    `"undefined"`/`"null"`/`"true"`/`"[object Object]"`/`""`, all of which
    `new Prisma.Decimal()` rejects → caught → dropped. (Two residual
    string values do get through — see A1.) Tests 13 and 14 pin the
    no-500 and no-markup behaviour.
  - **XSS:** the raw Json is never rendered. There is no
    `JSON.stringify(row.topProducts)`, no `dangerouslySetInnerHTML`
    (grep-confirmed across all of `src/app/admin`), and no HTML template
    string in either file — every untrusted value (`v.name`, `v.sku`,
    `row.sku`, `row.productName`, `row.variantName`) reaches the DOM only
    through JSX children, which React escapes by default. `productSlug`
    is interpolated into a `<Link href>` (`inventory/page.tsx:170`) — it
    is a DB-controlled slug, not user input, and it is a relative path
    under `/products/`, so it cannot become a `javascript:` URL. Test 14
    seeds `<img src=x onerror=alert(1)>` as an otherwise-valid `name` and
    asserts the unescaped markup is absent.
  - **Params are never echoed:** the `from`/`to` inputs render
    `from.toISOString()`/`to.toISOString()` — the *parsed* values, never
    the raw param (`:201`, `:212`); the region `<select>` renders the
    allowlisted value or `""`. Test 19 asserts `value="BOGUS"` and
    `value="2026-13-45"` never appear. (Framework-level echo of
    searchParams into the RSC flight payload is noted as A5, not a
    finding.)

- **Data residency:** checked, no finding. Both pages read the single
  primary client `db` (`@/lib/db`) — no replica, no secondary client, no
  cross-region routing, no external API call anywhere in the diff. No
  Ethiopia/Somalia customer data is touched: `DailySalesMetric` has no
  ET/SO writer, and `RegionalInventory` ET/SO rows are seed-created
  non-personal stock counts already resident in the same primary
  database. Nothing in this diff moves data between regions. The
  inventory page's ET/SO option set is recorded as advisory A4.

- **Money precision:** checked, no blocking finding. Every accumulation
  is `Prisma.Decimal`: the per-region subtotal is
  `bucket.revenueTotal.plus(row.revenue)` (`:179`) seeded from
  `new Prisma.Decimal(0)` (`:175`), and the top-variant merge uses
  `existing.revenue.plus(entry.revenue)` with `comparedTo` for sorting
  (`:131,138`). There is **no `Number()`, `parseFloat`, `+` or `reduce`
  over raw numbers on any revenue value** in either page — the only
  numeric `+=` is `ordersTotal` over the integer `ordersCount` column
  (`:178`) and `qty` (`:130`), both `Int`. Values are handed to
  `formatMoney` as `.toFixed(2)` strings per that module's stated
  contract. See A2 for the one residual double-conversion inside
  `formatMoney` itself (pre-existing, unreachable at realistic
  magnitudes).

- **No cross-currency financial misstatement:** checked, no finding, and
  verified by reading the render tree rather than the comment. Totals are
  accumulated into a `Map` keyed by `row.region` (`:164-182`); currency is
  derived per bucket as `regionCurrency(row.region)` (`:170`); every
  rendered money element — the subtotal (`:264`), each metric row
  (`:288`) and each top-variant row (`:311`) — formats with
  `bucket.currency`, and the per-row table is filtered to
  `row.region === bucket.region` (`:278`). There is **no element anywhere
  on the page that sums across buckets**: I traced every use of
  `regionSubtotals` and it is only ever `.map`ped into per-region
  `<section>`s, never reduced. `mergeTopVariants` is called per bucket
  (`:259`) on that bucket's own `topEntries`, so cross-region variant
  merging is structurally impossible too. Test 10 seeds a KE and a
  fixture-only ET row and asserts `KES 100.00` and `ETB 250.00` render
  separately and that `350.00` appears nowhere.

## Advisories (non-blocking, recorded for follow-up)

- **A1 (LOW) — `parseTopProducts` accepts the two non-finite Decimal
  string literals.** `analytics/page.tsx:113`,
  `new Prisma.Decimal(String(entry.revenue))`: decimal.js accepts the
  strings `"Infinity"`, `"-Infinity"` and `"NaN"`, so a first writer (or a
  hostile DB-write-capable actor) storing
  `{ ..., revenue: "Infinity" }` yields a top-variant row rendering as
  `KES ∞`, and `"NaN"` makes that bucket's `comparedTo` sort comparator
  return `NaN` (engine-defined ordering, no crash). Blast radius is
  strictly the top-variants table — the per-region subtotal comes from
  the `Decimal(14,2)` column, not from this Json — and there is no writer
  today, so this is not currently reachable. Suggested fix when M5-2f
  lands: add `if (!revenue.isFinite()) continue;` after the coercion.
  Same class as my "coercion guards that reject NaN still let falsy
  values through" learning, inverted.
- **A2 (LOW, pre-existing, not introduced here) — the Decimal chain ends
  in a `Number()` inside `formatMoney`.** `src/lib/money.ts:23` does
  `Number(amount)` before `Intl.NumberFormat`. Above roughly 4.5e13,
  adjacent doubles are spaced further apart than one cent, so a
  sufficiently large subtotal could display one cent off despite exact
  Decimal arithmetic. Unreachable in practice (KE revenue at that
  magnitude is not a real scenario) and the module is M5-1b-verified, but
  it is the precise reason the builder's exhaustive search for a
  Number()-divergent case at `Decimal(14,2)` magnitudes came up empty —
  the divergence lives one order of magnitude above the column bound, in
  the *display* conversion, not in the addition. Recording it so the next
  reviewer does not re-derive it.
- **A3 (LOW) — the item's input-validation logic sits inside
  coverage-excluded files.** `parseTopProducts`, `resolveRange`,
  `parseStrictUtcDate`, `parseAllowlisted` and `mergeTopVariants` are
  module-private to `analytics/page.tsx`, which
  `vitest.config.mts:332` excludes from coverage. The exclusion itself is
  justified (framework-coupled file, integration-tested), and the ADR
  explicitly directed the validator into the page module — but the net
  effect is that this item's Zod-equivalent validation layer is measured
  by nothing. Suggested follow-up (not required by this item): extract
  `parseTopProducts`/`resolveRange` into a framework-free
  `src/lib/analyticsView.ts`, unexcluded and unit-tested in-process,
  following the addressValidation.ts / searchParams.ts / orderTimeline.ts
  precedent already documented in that same config file.
- **A4 (LOW) — the inventory region `<select>` offers ET and SO, which
  run-state lists as out of horizon (U14).** `inventory/page.tsx:20`
  derives the option set from `Object.values(Region)`, so a future enum
  member is auto-exposed too. This is materially weaker than the
  M4-1-class allowlist finding in my learnings — no capability is
  granted, the rows are non-personal seeded stock counts already in the
  same primary DB, and the ADR argues the case explicitly (Decision 6)
  and flagged it as the architect's own open question (known-limit iii) —
  so it is recorded as advisory, not a finding. It should nonetheless be
  a human/product decision whether a KE deployment's admin UI surfaces
  ET/SO stock at all, and a hardcoded `["KE","ET","SO"] as const` would
  stop a future enum member inheriting exposure unreviewed.
- **A5 (INFORMATIONAL) — raw searchParams are echoed into the response
  body by the framework, not by the page.** Tests 8 and 20 correctly
  document that Next.js inlines a page's own searchParams into the RSC
  flight payload regardless of what the markup uses, which is why they
  assert on row testids rather than date substrings. This is not an XSS
  vector (React escapes `<` in the inlined flight chunks) and the echoed
  value is the requester's own input, so there is no oracle — but it does
  mean the page-level "never echoed" property holds for the *rendered
  markup* only, and test 19's `not.toContain('value="BOGUS"')` is
  correctly scoped to exactly that. Worth knowing before anyone writes a
  broader "param never appears in the response" assertion on an admin
  page and has it fail confusingly.
- **A6 (LOW, test hygiene) — two tests can pass without asserting their
  named property.** (i) Test 28 (`inventory/page.tsx` empty state) is
  wrapped in an `if (html.includes("low-stock-table")) { expect(200) }
  else { expect low-stock-empty }`. The ADR itself records that seed data
  (`onHand` 10–199, `safetyBuffer` 5, `reserved` 0–4) produces sub-10 rows
  in every region, so against a seeded dev DB the SO query is likely
  non-empty and the escape branch is taken — meaning the
  `low-stock-empty` branch may never actually be asserted. Prefer seeding
  a dedicated marker/region or filtering to fixture SKUs. (ii)
  `fetchResilient` (`test30:202-209`) retries once on **404** — which is
  precisely the status a genuine role rejection produces
  (`requireAdminRole()`'s `notFound()`). It does not mask a bug today:
  the builder's diagnostic evidence is documented in the helper's
  comment, I re-read `adminAuth.ts` in full and found **no leftover
  diagnostic code** (no `console.*`, no `TODO`, no `DEBUG` — grep
  confirmed; the file matches its M5-2a-verified shape), and critically
  **test 2 — the only test asserting a 404 as the correct outcome — uses
  plain `fetch`, not `fetchResilient`**, so the retry cannot swallow the
  authorization assertion. The residual risk is future drift: a new test
  that asserts an auth-rejection outcome via `fetchResilient` would
  silently retry past it. Recommend narrowing the helper to retry only
  when a 200 was expected (e.g. an explicit `expectStatus` argument) and
  adding a one-line comment forbidding its use in gate tests.
