## Re-verification of the two blocking findings

### F1 — FIXED. `src/lib/mpesa.ts:422-429`.

```ts
const resultCodeRaw = parsed?.ResultCode;
const validResultCodeShape =
  typeof resultCodeRaw === "number" ||
  (typeof resultCodeRaw === "string" && resultCodeRaw.trim() !== "");
const resultCode = Number(resultCodeRaw);
if (!validResultCodeShape || !Number.isFinite(resultCode)) {
  return indeterminate({ ...(parsed ?? {}) });
}
```

This is the sibling `parseStkCallback` guard (`mpesa.ts:555-559`) verbatim,
strengthened with `Number.isFinite`. I walked the falsy/garbled set by hand
against the actual predicate rather than trusting the description:

| value | shape guard | `Number.isFinite` | result |
|---|---|---|---|
| `""` | false (trim) | — | `indeterminate` |
| `" "` / `"   "` | false (trim) | — | `indeterminate` |
| `"\n"`, `"\t"`, `"\r\n"` | false (trim covers all JS whitespace incl. ` `, `﻿`) | — | `indeterminate` |
| `false` / `true` | false (typeof boolean) | — | `indeterminate` |
| `null` / `undefined` / absent | false (typeof object/undefined) | — | `indeterminate` |
| `[]`, `[0]`, `{}` | false (typeof object) | — | `indeterminate` |
| `"Infinity"`, `"-Infinity"`, `"1e999"` | true | false | `indeterminate` |
| number `NaN` | true (typeof number) | false | `indeterminate` |
| number `Infinity` | true | false | `indeterminate` |
| `"abc"` | true | false (`NaN`) | `indeterminate` |
| `"0"` / number `0` | true | true | `success` (correct) |
| `"1032"` / number `1032` | true | true | `failed` (correct) |

Every value in the falsy set now routes to `indeterminate`, and
`indeterminate` writes nothing: `reconcilePendingRow`
(`mpesaReconcileService.ts:154-171`) increments a counter and `console.warn`s,
or (only past 24h) CAS-abandons — it never reaches `handleMpesaCallback`, so
zero `PaymentTransaction`/`Order`/`OrderEvent`/inventory writes. Verified
end-to-end by test at `tests/test25-mpesa-reconcile.test.ts:591-622`, which
asserts `status` and `updatedAt` are both byte-identical after the run and
that the only OrderEvent is `CREATED`. Four unit cases (`""`, `"   "`,
`false`, `"\n"`) plus an `"Infinity"` case exist at :500-587. The tests are
non-trivial against the fix: each asserts `outcome === "indeterminate"` and
`resultCode === null`, both of which the pre-fix code returned differently
(`"success"`/`0` and `"failed"`/`Infinity` respectively).

Other values I probed for a residual slip: `"0x0"`, `"0b0"`, `"0e0"`, `"0.0"`,
`" 0 "`, `"-0"` all pass the guard and coerce to `0` → `success`. Each of
those *is* numerically the success code, so classifying them as success is the
correct reading of a (bizarrely formatted) Daraja envelope, not a bypass — the
attack shape that mattered was "nothing at all reads as success", and that is
closed. No finding.

Note the direction of the new asymmetry: `stkQuery` now rejects `Infinity`
where the sibling `parseStkCallback` (`mpesa.ts:559`, still `Number.isNaN`)
would classify it as a non-zero → failure code. `stkQuery` is now the
*stricter* of the two and the sibling's behaviour routes to the
Stripe-fallback (safe) branch, which is what the M4-2b sign-off already
accepted. No regression; recorded as advisory A7 for consistency only.

### F2 — FIXED. `src/lib/mpesaReconcileService.ts:435-457`.

The pass-B loop body now reads `report.scannedDeadLetter++` then
`try { await reconcileDeadLetterRow(row, ctx, report); } catch { report.errors++; console.error(...row.id...) }`
and continues. Verified against the four specific unwrapped call sites the
original finding cited — `findUnique` re-join (`:250`) and the three
unresolved-orphan `mpesaCallbackDeadLetter.update` calls (`:332`, `:342`,
`:351`) — all are now inside the loop's catch. The poison-row starvation
(`orderBy: { createdAt: "asc" }`) is closed: a permanently-throwing row costs
one `errors++` per run and never blocks a later row.

**Aggregate alert (specifically asked):** it still fires correctly for rows
that were successfully evaluated in a run where another row threw. The alert
block (`:463-479`) sits *after* the loop and, critically, is computed from a
fresh global query (`where: { resultCode: 0, reviewedAt: null }`) — not from
the in-memory report — so it reflects whatever the DB actually holds at
end-of-run, including both the successfully-corroborated rows and the row
whose write threw (that row is unresolved precisely *because* its write
failed, and it correctly still appears in the count). The regression test at
`:1417-1420` asserts the `UNRESOLVED ORPHAN MONEY` line was emitted in a run
where the middle of three rows threw, and `:1398-1406` asserts rows 1 and 3
were still corroborated with `errors === 1`. Without the loop catch this test
would fail on an unhandled rejection out of `runMpesaReconciliation`, so it is
genuinely coupled to the fix.

**Does it match pass A's pattern / does pass A need re-checking?** I re-read
pass A rather than assuming. There is a real structural difference, and it is
in pass A's favour on correctness but against it on robustness:

- Pass A protects itself *inside* `reconcilePendingRow` — `stkQuery`
  (`:145-151`), the abandon write (`:157-163`) and `handleMpesaCallback`
  (`:202-213`) each have their own try/catch, and every other statement in the
  function is throw-free (counter increments, a `Date.now()` subtraction, a
  `typeof` narrowing of `row.metadata`, `q.resultDesc.slice` on a
  guaranteed-string). So `reconcilePendingRow` genuinely cannot throw today.
- Pass A's *loop* (`:412-418`) therefore has **no** try/catch of its own,
  while pass B now has one at the loop.

Both passes satisfy ADR Decision 6.4 today. The asymmetry is a latent
maintenance hazard, not a live defect (any future unwrapped call added inside
`reconcilePendingRow` aborts the run and suppresses the aggregate alert, with
no test to catch it). Recorded as advisory A6, non-blocking — no live code
path currently throws out of pass A.

### A3 — FIXED, and the default preserves prior behaviour byte-for-byte.

`HandleMpesaCallbackOptions.reconciliationSource?: "stk_query" |
"dead_letter_rejoin"` (`mpesaCallbackService.ts:96`), threaded into
`CallbackCtx` (`:116`) via `opts.reconciliationSource ?? "stk_query"`
(`:1099`), consumed only by `reconciliationTag` (`:127-131`). Population (b)'s
DB re-join now passes `"dead_letter_rejoin"`
(`mpesaReconcileService.ts:280`). Confirmed the default is behaviour-neutral
on all three axes:

1. **Real M4-2b callbacks:** the webhook route passes only
   `{ requestStartMs, rawBody }`, so `source` defaults to `"callback"` and
   `reconciliationTag` returns `{}` — the `reconciliationSource` key is never
   emitted at all, regardless of its default. `buildConfirmMetadataPatch`
   still early-returns the untagged `base` when the tag is empty (`:356`), so
   every metadata/OrderEvent payload is byte-identical to M4-2b.
2. **Population (a):** sets `source: "reconciliation"` and does *not* set
   `reconciliationSource`, so the default yields exactly the previous
   `{ reconciled: true, reconciliationSource: "stk_query" }`. Asserted at
   `tests/test25-mpesa-reconcile.test.ts:676`.
3. **Control flow:** the new field is read at exactly one place
   (`reconciliationTag`) and nowhere else — grep across `src/` confirms.
   Auto-retry suppression is still keyed on `ctx.source` alone
   (`mpesaCallbackService.ts:995-997`, still the first statement of
   `retryOrFallback`, above the `AUTO_RETRY_RESULT_CODES` check), so a
   reconciliation-sourced `1037` still cannot reach `createMpesaStkPush`.

Red-teamed the dedupe interaction: `findEvent` (`:405-418`) matches on
`orderId` + `eventType` + a **single** JSON path key, never the whole payload,
so a row seen once via `dead_letter_rejoin` and once via `stk_query` still
dedupes correctly and cannot produce a duplicate OrderEvent. The tag value is
ops metadata only. Also confirmed the two literals are a closed union — an
attacker-supplied callback body cannot inject either value, since the webhook
route never spreads the parsed body into the options object.

## Advisories (non-blocking, retained follow-ups — do not gate on these)

- **A1 — a reconciliation-sourced synthetic can create a *false* dead-letter
  row.** If `resolveRow` finds nothing for a population-(a) synthetic (only
  reachable if the `PaymentTransaction` row disappeared or had its
  `providerTxId` rewritten mid-run — neither happens today, per M4-2b
  Decision 6's "`providerTxId` is never in any SET clause" invariant),
  `handleMpesaCallback` falls through to `recordOrphan`
  (`mpesaCallbackService.ts:1105-1107`), writing a `resultCode: 0`,
  `amount: null`, receipt-less row into the human refund queue. Practically
  unreachable. Worth a guard (reconciliation source → count and skip rather
  than dead-letter) when this area is next touched.
- **A2 — per-row `console.error` on the contradiction path**
  (`mpesaReconcileService.ts:349`) prints the `checkoutRequestId` every run;
  ~96 lines per contradicting row per day while under 24h. Defensible (rare,
  high-signal) but noted. No secret or PII in the line.
- **A4 — counter accuracy:** `report.scannedPending++` (`:152`) is incremented
  after `stkQuery` returns, so rows whose query *throws* (only possible on
  missing `MPESA_SHORTCODE`/`MPESA_PASSKEY`) are counted in `errors` but not
  in `scannedPending`. Cosmetic; no security impact.
- **A5 — test 20's "zero Daraja calls"** is asserted only via unchanged row
  counts, with no fetch-mock call-count assertion (the route cannot be
  injected with `fetchImpl`). The property holds by construction and I
  verified it by reading; the label claims slightly more than the test proves.
- **A6 (new, from the F2 re-check) — pass A's loop has no try/catch, unlike
  pass B's.** `mpesaReconcileService.ts:412-418` relies on
  `reconcilePendingRow` being throw-free by construction, which it is today
  (every external call inside it is individually wrapped). Any future
  unwrapped call added to that function reintroduces exactly the F2 failure
  mode — run abort plus loss of the aggregate `UNRESOLVED ORPHAN MONEY`
  alert — with no test to catch it. Symmetry with pass B's loop-level catch
  would make the invariant structural rather than incidental. Not blocking:
  no current path throws.
- **A7 (new, consistency only) — `parseStkCallback` (`mpesa.ts:559`) still
  uses `Number.isNaN` where `stkQuery` now uses `Number.isFinite`.** A real
  callback carrying `"Infinity"` is therefore classified as a non-zero
  (failure) code rather than malformed. That routes to the Stripe-fallback
  branch, which the M4-2b sign-off already accepted as the safe direction, so
  this is a wording/consistency item, not a defect. Aligning the two would
  make the module's two parsers identical.
- **A8 (new, test coverage only) — the `"dead_letter_rejoin"` tag value has no
  assertion.** Repo-wide grep finds it only in the type union, the doc
  comments and the single call site; `tests/test25-mpesa-reconcile.test.ts:676`
  asserts the `"stk_query"` value for population (a), but no test asserts the
  new value lands in a population-(b) OrderEvent/metadata payload. The field
  is ops metadata with no control-flow effect, so this is coverage hygiene,
  not a security gap.
