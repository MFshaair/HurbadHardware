# Security review — M4-1 (Stripe Embedded Checkout session creation, HRH-47)

STATUS: CLEAR

No blocking finding. Four findings recorded (F1 LOW-MEDIUM/advisory, binding
on the M-Pesa item; F2 LOW; F3 LOW; F4 LOW/process). None is exploitable from
any HTTP route today: every one of them requires either a payment provider
that does not exist yet in this repo (F1), a value that cannot reach the
vulnerable sink before an ownership check has already resolved it to a real

## Checked

- **PCI scope — no finding.** No new file contains a card, CVC, PAN, expiry,
  or `payment_method` field anywhere. Traced `{ orderId, cardNumber: "4242…" }`
  end to end: `route.ts:54-62` computes `Object.keys(body)` and rejects on any
  key outside the `Set(["orderId"])` allowlist — a hard 400 *before* `orderId`
  is even read (`:64`), before `createStripeCheckoutSession` is called, and
  before anything is logged. This is genuinely reject-unknown, not
  Zod-`.strip()`-style silent-ignore, and it is stronger than the PRD DoD's
  Zod default would have been (see F4 note). `PaymentTransaction.metadata` is
  never written by this diff at all (both `paymentTransaction.create` calls,
  `:351-360` and `:367-376`, set only
  `orderId/provider/idempotencyKey/amount/currency/status`). Stripe-side
  `metadata` is a two-key literal built from server-read values only
  (`paymentService.ts:391`), asserted byte-exact in
  `test20:182` and `test19:79`. No log statement in any new file receives a
  request body: the only `console.*` added in this diff is
  `paymentService.ts:116`, which logs `err.message` for `OrderNotFoundError`,
  whose message is constructed from the orderId alone (`:48-51`). test21:215-246
  proves the card-field body reaches neither the response, nor
  `PaymentTransaction`, nor `console.error`.

- **Order ownership — verified, not claimed.** `paymentService.ts:230-260`.
  The `SELECT … FOR UPDATE` on `"Order"` (`:230-235`) is taken first; the
  typed re-read (`:240-243`) and **both** ownership branches run inside that
  same `db.$transaction`, under the lock, before any status/money/attempt
  logic. Authenticated path: `order.userId !== null` requires
  `userId === order.userId`, where `userId` comes only from
  `auth.api.getSession()` server-side (`route.ts:35-36`) and can never be
  supplied in the body (allowlist above). Guest path: requires a present
  `sessionId` (from the httpOnly cart cookie, `route.ts:37` →
  `cartCookie.getCartSessionId`, never from the body) **and** a matching
  `CREATED` `OrderEvent` whose `payload.sessionId` equals it — confirmed
  against the producer side: `reservationService.ts:521` really does record
  `sessionId: cart.sessionId` in that payload, so this is a real check, not
  one matching a field that is always absent. A logged-out requester hitting
  an authenticated user's order takes the first branch (`userId` is `null`,
  never equal to a non-null `order.userId`) → rejected. No-oracle: every
  failure — nonexistent order, wrong user, wrong/missing guest cookie — throws
  the same `OrderNotFoundError`, mapped at `:111-118` to an identical
  `404 {"error":"Order not found"}` with no id echoed. Proven at the HTTP
  layer with a byte-comparison of the two bodies in test21:262-331, and at the
  service layer in test20:576-610.

- **Payment idempotency / attempt reuse — no finding.** The idempotency key is
  never client-supplied and never client-selectable: it is either
  `randomUUID()` (`:350`, `:366`) or read off a row found by
  `findMany({ where: { orderId } })` (`:301`) — keyed solely on the `orderId`
  that already passed the ownership check under the same lock. There is no
  lookup by `idempotencyKey`, by `providerTxId`, or by any request value
  anywhere in the module (grepped), so a client cannot steer which row is
  reused or reach another order's row. The duplicate predicate
  (CONFIRMED → 409, PENDING → 409, INITIATED <120s → 409, INITIATED
  120s–24h → reuse row+key, INITIATED >24h → CAS to FAILED + fresh row) all
  executes inside the `Order` row lock, so two concurrent requests serialize;
  test20:207-235 proves exactly one row and exactly one Stripe call under real
  concurrency against real Postgres. Phase C is a CAS
  (`WHERE id = … AND status = 'INITIATED'`, `:471-478`) with `affected !== 1`
  → 409, so a lost race cannot double-write. `idempotency_key_in_use` from
  Stripe correctly leaves the row INITIATED rather than FAILED (`:426-431`),
  so the sibling request can still complete. See F1 for the one gap: the
  predicate is scoped by `orderId` but not by `provider`.

- **Money integrity — real, and it does block the Stripe call.** Traced:
  `prepareAttempt` builds line items from `order.items[].unitPrice/quantity`
  plus `order.taxAmount`/`order.shippingAmount` (all read from the frozen DB
  rows), sums them into `sumMinor`, and at `:291-298` compares against
  `toMinorUnits(order.totalAmount)`, throwing `PaymentAmountMismatchError`
  *inside* Phase A's transaction — i.e. before the transaction commits and
  therefore before Phase B (`:418`) is ever reached, and it also rolls back
  the `PaymentTransaction` row creation, which happens later at `:301+`.
  Confirmed there is no `catch` between the throw and the caller that could
  swallow it, and `paymentErrorResponse` deliberately returns `null` for it
  (`:143`), forcing the route to re-throw (`route.ts:77`) → 500 + server log,
  never a friendly retry. `toMinorUnits` additionally rejects non-integer
  minor units (`:159-167`). No amount, currency, quantity, or line item is
  ever read from the request body — the body cannot contain such a key at all
  (allowlist), and `stripeInput.currency` comes from `order.currency`
  (`:384`). `Order` has no `discountAmount` column (schema `:202-205`), so
  subtotal+tax+shipping is the complete decomposition; the assertion cannot
  false-positive on a missing component. test20:432-446 proves no Stripe call
  and no row on mismatch.

- **`ui_mode` correction — applied, not merely claimed.** Grepped
  `src/lib/stripe.ts`: the single `ui_mode` occurrence is line 100,
  `ui_mode: "embedded_page"` (literal). `success_url`/`cancel_url` appear in
  this file only inside the pre-existing, untouched `createSetupCheckSession`
  U1 smoke helper (`:45-46`); they are entirely absent from
  `createEmbeddedCheckoutSession`'s params object (`:97-117`) — absent, not
  empty strings. test19:66-72 asserts both the literal value and
  `not.toHaveProperty` for the two URLs.

- **Auth — no finding.** No credential field, no custom JWT, no custom session
  table introduced. Identity comes exclusively from `auth.api.getSession()`
  (better-auth, AHD8) at `route.ts:35`. No admin route or admin-only surface is
  added by this diff, so the admin-role and presence-check-middleware rules are
  not engaged here (`src/middleware.ts` is untouched — confirmed it is not in
  the changed-file list and not referenced by any new file). The new route is
  intentionally reachable unauthenticated (guest checkout), but every write it
  can cause is gated behind the ownership check above and bounded by the
  duplicate-attempt predicate (after one success the row is PENDING → all
  further calls 409), so it is not an unauthenticated write amplifier.

- **Secrets — no finding.** `STRIPE_SECRET_KEY` is read in exactly one place
  (`stripe.ts:10`, server-only module, no `"use client"`, not imported by any
  client component — `StripeCheckout.tsx` imports only `@stripe/stripe-js` and
  `@stripe/react-stripe-js`). It never appears in a response body (the route
  returns exactly `{ clientSecret, paymentTransactionId }`, `route.ts:71`), in
  a log, or in an error path — the Stripe error branch stores only
  `err.code`/truncated `err.message` in the DB. `STRIPE_WEBHOOK_SECRET` is not
  referenced by any file in this diff. `StripeCheckout.tsx:26` reads
  `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` — confirmed it is the publishable key,
  not the secret key, and repo-wide grep shows no `NEXT_PUBLIC_*` var holding
  an `sk_`-shaped value. No real key value is introduced anywhere: every `.env*`
  hit is still a `REPLACE_ME` placeholder, and the only key-shaped literals in
  tests are obvious fakes (`sk_test_mock_key_for_m4_check`). Test mocking is
  test-layer only — `vi.mock("../src/lib/stripe")` / `vi.doMock("stripe")` in
  the test files; there is no `NODE_ENV`/env-flag branch inside `route.ts`,
  `paymentService.ts`, or `stripe.ts` that swaps in fake behaviour at runtime
  (grepped `NODE_ENV` across all changed `src/` files: zero hits).

- **Error responses — no leak.** Traced the whole mapping. The Stripe branch
  (`paymentService.ts:425-462`) captures `err.code`/`err.message` into the
  *database* only, then throws a parameterless `StripeUnavailableError` whose
  own message is a fixed string; the underlying `StripeError` object is
  dropped at that point and never referenced again. `paymentErrorResponse`'s
  502 case (`:137-142`) returns a hardcoded body literal — no `err.message`,
  no `requestId`, no `raw`, no `statusCode`, and no interpolation of any kind.
  Same for 404 (hardcoded). The two 409s that do echo a field echo only
  `paymentStatus` (an enum this requester already owns) and `currency` — both
  are properties of the requester's own order, disclosed only after ownership
  passed, so neither is an oracle. test20:349-384 asserts the 502 body contains
  neither the Stripe message nor the request id.

- **Injection / SSRF / unsafe render — no finding beyond F2.** `return_url` is
  built solely from `process.env.NEXT_PUBLIC_APP_URL` (`:179`), which is
  validated as an absolute `http(s)` URL and fails closed before any row is
  created; the host/scheme portion is not client-influencable at all, so there
  is no open-redirect or SSRF primitive (see F2 for the query-string nit). All
  SQL is either Prisma client calls or tagged-template `$queryRaw`/`$executeRaw`
  with `${}` parameter binding — no string-concatenated SQL anywhere in the new
  code (re-read every raw block: `:230`, `:331`, `:439`, `:471`). The Prisma
  JSON filter on the attacker-supplied cookie (`:252-258`) is likewise
  parameterized. `StripeCheckout.tsx` never renders `clientSecret` into the
  DOM — it is returned from `fetchClientSecret` straight into
  `EmbeddedCheckoutProvider`'s `options` (`:63`, `:74`); no
  `dangerouslySetInnerHTML`, no URL interpolation, no `innerHTML` in the file.
  The only rendered dynamic string is `error`, and it is rendered as a React
  text child (auto-escaped) inside `role="alert"` (`:65-71`).

- **Admin audit log — not applicable, checked.** This diff adds no admin
  mutation and no admin route. The customer-facing audit trail is nonetheless
  written on every branch: `PAYMENT_SESSION_CREATED` on success (`:479-486`),
  `PAYMENT_SESSION_FAILED` on Stripe failure (`:447-458`) and on stale-row
  expiry (`:338-349`), each in the same transaction as the status change.
  `AdminAuditLog` is correctly untouched.

- **Data residency — one advisory (F3).** No infra/region config is changed;
  nothing in this diff reads a region from the PRD. See F3 on the currency
  allowlist.

## Findings

### F1 — LOW-MEDIUM (advisory; binding on the M-Pesa item, not on M4-1)
`src/lib/paymentService.ts:301` — the duplicate-attempt/crash-recovery
predicate selects `paymentTransaction.findMany({ where: { orderId } })` with
**no `provider: "stripe"` filter**, and the crash-recovery branch (`:314-326`)
then adopts whatever INITIATED row it finds: it reuses that row's id and its
`idempotencyKey`, and Phase C (`:471-477`) stamps a Stripe Checkout Session id
into that row's `providerTxId` while its `provider` column still says whatever
it originally said. Today this is unreachable — `"stripe"` is the only value
this repo ever writes — so it is not a defect in M4-1 as shipped. The moment
M4-2/M-Pesa lands, an abandoned INITIATED M-Pesa row 2 minutes to 24 hours old
would be silently converted into a Stripe attempt (and a
`PAYMENT_SESSION_FAILED` `OrderEvent` claiming `provider: "stripe"` would be
written for an M-Pesa row at `:338-349`), corrupting the money-path audit trail
and any provider-scoped webhook reconciliation. Note that the ADR itself does
not scope the predicate by provider (grepped: `provider` never appears in its
Decision 2b/3 sections), so this is a design gap, not a builder deviation.
**Routing:** record now, enforce at whichever item introduces the second
provider — add `provider: "stripe"` to the `findMany` filter (and decide
explicitly whether a live *other-provider* attempt should block a Stripe one;
"block" is probably right, but it should be a stated decision, not a
side-effect of an unfiltered query). Same "record now, enforce at the next
item" mechanism used for M3-1 F8 and M3-2 F1/F2.

### F2 — LOW
`src/lib/paymentService.ts:185` — `buildReturnUrl` interpolates the raw,
client-supplied `orderId` into a URL query string with no
`encodeURIComponent`. It is called at `:408`, *before* any validation beyond
"non-empty string" (`route.ts:65`). Not currently exploitable: the resulting
URL is only ever sent to Stripe after `prepareAttempt` has matched the id to a
real `Order` row (a cuid, no URL-significant characters), and a bad id throws
`OrderNotFoundError` first — so a crafted value (`&`, `#`, `%`) can never reach
Stripe or a browser. Recommend `encodeURIComponent(orderId)` anyway as defence
in depth, consistent with the M3-3a finding of the same class recorded in
`docs/agents/learnings/security-reviewer.md`; today the safety is positional
(which call happens first), not local to the function.

### F3 — LOW (data residency / product)
`src/lib/paymentService.ts:40` — `SUPPORTED_STRIPE_CURRENCIES` contains
`ETB` and `SOS` alongside `KES`. Ethiopia/Somalia are explicitly out of scope
for this run (run-state NORTH STAR / U14), and Somalia's data-residency legal
opinion is an open escalation. An allowlist entry is the only gate between an
ET/SO order and Stripe's global processing of that order's customer email and
line-item names; nothing else in the code path re-checks region. Unreachable
today (the MVP creates KE orders only) and the ADR's Known limits already flags
Stripe ETB/SOS support as unverified — but the fail-safe default is to ship
`KES` only and add the other two with the product/legal decision that admits
them, rather than to pre-open the door. Not blocking.

### F4 — LOW (process / coverage hygiene, no runtime impact)
`vitest.config.mts:226` — the pre-existing `"src/app/api/checkout/**"` glob
(argued in M3-3 for `POST /api/checkout` specifically) now silently also
excludes the new `create-stripe-session/route.ts`, which is where this item's
unknown-key rejection lives. The exclusion is *substantively* justified (the
route calls `auth.api.getSession()`/`next/headers` and is genuinely only
reachable via test21's spawned dev server, and that test does cover the
allowlist at `:215-258`), so this is not the "dodging coverage on business
logic" case — but it is exactly the silent-inheritance pattern security-reviewer
M2-1 F3 asked to be avoided by listing route files explicitly. Suggest
replacing the glob with explicit filenames. The new `src/lib/paymentService.ts`
is correctly **not** excluded.

## Known limits (could not assess without running code — flagged, not guessed)
- I have no Bash and did not execute the suite; I am relying on the
  orchestrator's independent local-check run (264 passed/2 skipped) for
  "these tests pass," and reviewed the test *code* directly for whether they
  assert the right things.
- I could not verify that any of the new tests were proven non-trivial (the
  "temporarily break the thing under test and watch it fail" step). The
  ownership and no-oracle tests (test21:262-331) are the ones where this matters
  most — they would still pass if the guest branch were deleted *and* the cookie
  happened to be absent. They do send a real, wrong cookie value under the real
  cookie name (`hurbad_cart=<random uuid>`, `:270`), which is the correct shape
  per my learnings, but the cookie name is **hardcoded** rather than derived at
  runtime from a live `Set-Cookie` — if `CART_COOKIE_NAME` ever drifts (it is
  already env-derived: `__Host-hurbad_cart` in production) this test silently
  degrades into the weaker no-cookie path and still passes. Reproduction request
  for the builder rather than a finding: confirm the forged-cookie ownership
  test fails when the guest branch (`paymentService.ts:250-260`) is temporarily
  removed.
- `StripeCheckout.tsx` is not mounted by any page yet, and `/checkout/complete`
  (the `return_url` target) does not exist — both confirmed by grep. No security
  consequence for M4-1; flagged so HRH-48 does not assume a return page exists.
- A guest whose cart cookie rotates between order creation and payment
  (`src/lib/auth.ts:105` rotates on login *and* logout) permanently loses the
  ability to pay for that order (404 forever). Availability/UX, correctly
  fail-closed from a security standpoint, but it should be a deliberate
  known limit rather than a surprise.
- The route's body validation is hand-rolled rather than Zod (the PRD DoD names
  Zod). Recorded as consistent-with-repo-precedent and *stricter* than Zod's
  default object behaviour, not as a finding — but if a future item introduces
  Zod here, it must use `.strict()`, or this reject-unknown-keys property (the
  thing that makes a `cardNumber` field a hard 400) silently regresses to
  silent-strip.
