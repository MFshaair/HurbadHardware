## The seven questions asked

### 1. Cross-user address access via a forged `savedAddressId` — VERIFIED, holds
Verified by reading the route, not the builder's claim.
`src/app/api/addresses/[id]/route.ts:19-33`: `GET` independently calls
`auth.api.getSession({ headers: await headers() })`, returns 401 with no
session, then `findUnique({ where: { id } })` and rejects with **404** (not
403 — no existence disclosure) when `existing.userId !== session.user.id`.
`ReviewStep.tsx:68-88` never renders `draft.savedAddressId`'s own contents:
it re-fetches through that route and renders only `body.address.*`. Any
non-ok response (404 cross-user, 401 guest, network error) sets
`addressLoadState="invalid"` and renders the "no longer available" panel
(`:96-110`) — it never falls back to draft-supplied data.

Two independent boundaries, both correct: the list at
`address/page.tsx:40-45` is scoped `where: { userId: session.user.id }` from
this page's own `getSession()` call, and the per-id consumption re-checks.
Note this is the *split* ownership-check form (findUnique → compare →
act) flagged in my own learnings; here the "act" is a read only, no mutation
by id, so the split carries no reassignment risk.

Red-team pass: forged id for another user's address → 404 → invalid panel.
Forged id as a guest → 401 → invalid panel. Forged id that doesn't exist →
404. Draft with `addressMode:"saved"` and no id → `draftHasAddress()`
(`CheckoutDraftContext.tsx:110`) is false → redirect to `/checkout/address`.
Draft with `addressMode:"new"` plus a `savedAddressId` → the "new" branch at
`ReviewStep.tsx:63` wins and the id is never fetched or used.

### 2. Guest address persistence — VERIFIED, holds on both happy and error paths
`POST /api/addresses` appears exactly once in the diff,
`AddressStep.tsx:113-133`, gated on `isAuthenticated && saveNewAddress`.
Triple-gated in practice: (a) the checkbox is only rendered for an
authenticated user (`:277-287`), so a guest cannot set `saveNewAddress`;
(b) the call site re-tests `isAuthenticated`, a server-computed prop from
`address/page.tsx:37-38`'s own `getSession()`; (c) the route itself 401s
without a session (`api/addresses/route.ts:31-34`). No auto-save anywhere —
the `mode === "saved"` branch returns at `:99-101` before any fetch, and the
"new" branch with the box unchecked falls straight through to
`setNewAddress(form, false)` + `router.push` with no network call. Error
path checked specifically: `!res.ok` (`:121-126`) and the `catch`
(`:127-131`) both `return` *before* `setNewAddress`/navigation — no
save-then-fail-then-silently-save-again path. `setNewAddress`'s second
argument is `isAuthenticated && saveNewAddress`, so a guest draft can never
even carry `saveNewAddress: true`.

### 3. sessionStorage PII scope — mostly holds; see F1
Stored fields are exactly: `version`, `addressMode`, `savedAddressId`,
`newAddress{fullName, phone, region, city, postalCode, street}`,
`saveNewAddress`, `paymentProvider`, `updatedAt`
(`checkoutDraft.ts:27-46`). **No price, tax, quantity, currency, subtotal or
total** — confirmed by reading the whole module and every `setDraft` call in
`CheckoutDraftContext.tsx:58-85`. No email, no card data, no payment
credential, no user id, no session token. `localStorage` is not used
anywhere (repo-wide grep: one comment in `useCart.ts` saying it is
deliberately not used). TTL 60 min (`:25`, enforced at `:119`), version
gate + wholesale-discard-on-invalid (`:81-97`) are real and unit-tested
(`test16` tier A, lines 72-106). One discrepancy on `region` — F1 below.

### 4. XSS / injection on `/checkout/review` — checked, no finding
Every draft-derived string is rendered through plain JSX interpolation:
`ReviewStep.tsx:120-125` (`fullName`, `phone`, `street`, `city`, `region`,
`postalCode`) and `:136` (a lookup into the hardcoded `PROVIDER_LABELS` map,
never the raw provider string, and the draft validator already constrains it
to `"stripe" | "mpesa" | null`). Repo-wide grep for
`dangerouslySetInnerHTML|innerHTML|document.write|eval(` across `src/`
returns zero hits. React escapes all of these. Same for
`AddressStep.tsx:165-170`, which renders the user's own DB rows via JSX.

### 5. "Place order" inert-by-construction — VERIFIED by reading the code
`ReviewStep.tsx:152-163`: `<button type="button">` (not a submit, not inside
a `<form>`) whose only handler is `onClick={() => setPlaceOrderClicked(true)}`
— a local `useState` flip. Grep of the entire `src/app/checkout/` tree finds
exactly two `fetch` call sites: `AddressStep.tsx:116` (the opt-in address
save) and `ReviewStep.tsx:70` (the ownership re-check GET). There is no
server action (`"use server"` absent from the tree), no form action, no
route handler under `src/app/checkout/`. Creating an `Order`/
`InventoryReservation`/`PaymentTransaction` is therefore impossible from
this control — no reachable code path exists, which is stronger than the
test's row-count assertion.

### 6. Auth/session in the new pages — checked, no finding
`src/middleware.ts:22` matcher is still `["/profile/:path*"]` — `/checkout/*`
is deliberately **not** behind the presence-check middleware at all
(checkout is guest-accessible by design), so there is no
presence-vs-validity gap to exploit here. Every server-side auth decision in
the new code comes from an independent Node-runtime `auth.api.getSession()`:
`checkoutCart.ts:31` (shared by all three pages) and again at
`address/page.tsx:37` for the saved-address query. A forged/expired session
cookie yields `session === null` there and the visitor is treated as a
guest — empty saved-address list, no save checkbox, and the API 401s. The
pattern matches `/profile` and `/cart`. Payment-method availability
(`payment/page.tsx:35`, `showMpesa={context.region === "KE"}`) is derived
from the server-side `resolveRegion()`/cart region, never from the client.

### 7. Standard sweep — checked, no finding
Secrets: no literal value, no `process.env` read, and no `console.*` call
anywhere under `src/app/checkout/` or in `checkoutDraft.ts` (grep,
case-insensitive, for `console.|process.env|sk_live|sk_test|SECRET|api_key`
→ zero hits). Nothing logs a name, phone or street. New write paths: exactly
one (`POST /api/addresses`) and it is authenticated (F2/F3 above); the
draft's own writes are client-local. Open redirect / SSRF: every navigation
target in the tree is a hardcoded literal (`page.tsx:7`,
`AddressStep.tsx:100,136`, `PaymentStep.tsx:27,75`, `ReviewStep.tsx:52,56`);
no `searchParams`/`useSearchParams` is read anywhere in the tree; the only
dynamic URL is the same-origin relative fetch in F2 below.

## Findings

### F1 (LOW — doc/code contradiction with a real forward-risk) — `region` IS stored in the draft
`src/lib/checkoutDraft.ts:30` stores `region` inside `NewAddressDraft`, but
line 19 of that same file asserts "No price, tax, quantity, currency, or
region is ever stored here", restating ADR Decision 4 #2 (`:109-112`). The
ADR contradicts itself — Decision 3's payload (`:79-81`) explicitly includes
`region`. **Not exploitable today**: I traced every consumer, and no money,
tax, currency or inventory value is derived from the draft. Pricing region
comes only from `checkoutCart.ts:22-38` (`resolveRegion()` reading
`NEXT_PUBLIC_REGION` server-side, per `src/lib/region.ts:38-50`, or the
cart's own persisted region), and `CartSummary` receives `context.region`,
never the draft.

The forward risk is concrete, because ADR Decision 3 (`:94-96`) instructs
M3-3 to hand `newAddress` to `validateAddressBody` unchanged: a client that
edits `newAddress.region` in devtools would then control the region attached
to the created `Address` — and if any M3-3 code derives price/tax/currency
from the shipping address's region rather than the deployment region, that
becomes a client-trusted-price bug. Fix the comment and the ADR to say what
is actually true ("the shipping address's own destination region is stored;
it is never a pricing input"), and record the M3-3 constraint explicitly.
Routing: `storefront-admin-engineer` for the comment,
`platform-architect` for the ADR text; binding on whoever builds M3-3.

### F2 (LOW) — unencoded attacker-writable value in a URL path
`src/app/checkout/review/ReviewStep.tsx:70`:
`fetch(\`/api/addresses/${draft.savedAddressId}\`)`. `savedAddressId` is
validated only as `typeof === "string"` (`checkoutDraft.ts:85`) and the
module's own header correctly declares it untrusted. A value containing
`../` (e.g. `../cart/add`) is normalized by the browser before dispatch, so
the request lands on a *different* same-origin endpoint than intended.
Impact is bounded to self-XSS territory — writing the victim's
`sessionStorage` already requires an XSS on this origin — and the reachable
endpoints are GET-only route handlers, so I could find no privilege gain.
Still, wrap it: `encodeURIComponent(draft.savedAddressId)`. Routing:
`storefront-admin-engineer`.

### F3 (LOW) — duplicate PII rows from resubmission on the address step
`src/app/checkout/address/AddressStep.tsx:113-133`. `POST /api/addresses`
has no idempotency: the `saving` guard is set *inside* the async handler, so
a fast double-click can dispatch two creates, and after a failed attempt the
user can retry indefinitely, each successful retry creating another
`Address` row with the same name/phone/street. No cross-user impact and no
money involved — this is PII-minimization/data-hygiene, not authz. Consider
a submitting ref (not state) and/or a dedupe on
`(userId, fullName, phone, street, city, postalCode)`. Routing:
`storefront-admin-engineer`, non-blocking.

### F4 (LOW, pre-existing pattern) — full Prisma rows serialized into the RSC payload
`src/app/checkout/address/page.tsx:41-44` passes `db.address.findMany(...)`
results straight into `<AddressStep initialAddresses={...}>`, so `userId`,
`createdAt` and `updatedAt` are serialized to the client even though
`AddressStep.tsx:13-22`'s `SavedAddress` type comment claims it is "never
the raw Prisma Address row" (TypeScript narrows the type; it does not strip
the runtime object). Only the viewer's own data is exposed, and
`src/app/profile/page.tsx:32-35` has done the same since M1-3, so this is
not a regression — but the comment is inaccurate, and an explicit `select`
would make it true. Routing: `storefront-admin-engineer`, bundle if
convenient.

### F5 (MEDIUM, carried forward from M3-1 F8 — NOT introduced here, and NOT triggered here)
`src/lib/cartService.ts:294-299` still lacks `userId: null` on the
sessionId branch, so a leaked `hurbad_cart` cookie still resolves a
user-owned cart. `checkoutCart.ts:35` calls `findActiveCart` and so inherits
this: a cookie holder can view the victim's cart contents at
`/checkout/*`, exactly as they already could at `/cart`. **M3-1's sign-off
made closing F8 a hard prerequisite for "M3-2/M3-3 attaching guest email +
shipping address to the cart" — I verified M3-3a does not do that.** The
address lives in per-tab `sessionStorage`, never on `ShoppingCart` (no
schema change, ADR Decision 8 holds), so no PII is added to the surface F8
exposes. Still open, still a hard blocker for M3-3. Routing:
`catalog-inventory-engineer`.

## Checked (iron rules — all of them, explicitly)
- **PCI scope:** checked, no finding. No card field is collected anywhere
  in this diff — `payment/page.tsx:5-8` and `PaymentStep.tsx:14-19` capture
  a provider *choice* only. No PAN-shaped literal, no Stripe token, no
  M-Pesa credential appears in any changed file, and nothing card-related is
  written to `sessionStorage` or the DB.
- **Payment idempotency:** N/A for this diff — no webhook handler, no
  payment endpoint, no order/stock mutation exists here (see #5). Forward
  note for M4: ADR's own Known Limits (`:187-191`) correctly forbid using
  this draft as post-redirect authoritative state; the idempotency key must
  live on `PaymentTransaction`, never in `sessionStorage`.
- **Auth:** checked, no finding. No hand-rolled credential field, no custom
  JWT, no custom session table; AHD8 holds. `better-auth`'s
  `auth.api.getSession()` is called independently server-side in every new
  page path (`checkoutCart.ts:31`, `address/page.tsx:37`) and in both
  address API routes. `login/page.tsx:55` adds only a client-side
  `clearCheckoutDraft()` after a successful sign-in — it does not touch the
  auth request, its single error branch, or the enumeration-safe
  single-request shape established in M1-2 (re-read lines 25-62 to confirm
  the fetch/error path is byte-for-byte unchanged in behaviour).
- **Presence-check middleware is never the real gate:** checked, no
  finding. `src/middleware.ts:22` does not match `/checkout/*` at all, so
  nothing in this diff can rely on it; all checkout auth decisions are
  Node-runtime `getSession()` calls. No new page depends on presence-only
  checking, so no new forged-cookie test is owed by this item (the existing
  `/profile` one still covers the only presence-gated route).
- **Secrets:** checked, no finding. Zero `process.env` reads, zero
  `console.*` calls, zero literal values in the entire `src/app/checkout/`
  tree and `checkoutDraft.ts`. No secret, card number or credential is
  logged, and no `.env` file is touched by this diff.
- **Admin audit log:** N/A — this diff contains no admin route and no admin
  mutation. `AdminAuditLog` is untouched.
- **Input validation:** server-side validation is present and unchanged
  (`validateAddressBody`, `src/lib/addressValidation.ts:30-89`) and it does
  enforce the `Region` enum server-side (`:51-56`), so the F1 region value
  cannot be a free-form string in the DB. The client-side
  `requiredFilled` check at `AddressStep.tsx:107` is UX only and is
  correctly duplicated server-side. Two carried caveats, neither new here:
  the repo still hand-rolls this rather than using Zod as the PRD's
  Definition of Done specifies (M1-3 F7, deferred to M6), and there is still
  no maximum length on any address field, so an authenticated user can store
  arbitrarily long strings. Neither is introduced or worsened by M3-3a.
- **Data residency:** checked, no finding. Nothing new routes
  Ethiopia/Somalia data anywhere: region is resolved from
  `NEXT_PUBLIC_REGION` server-side per deployment (`src/lib/region.ts`),
  consistent with run-state's active `eu-west-2`/London decision for
  KE/SO, and this diff adds no new external call, no new datastore and no
  cross-region read. The draft never leaves the user's own browser tab.
