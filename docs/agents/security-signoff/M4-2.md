Reviewed by reading every changed file in full (not a summary):
`src/lib/paymentErrors.ts`, `src/lib/mpesaService.ts`, `src/lib/mpesa.ts`,

The item's core security work (the M4-1 F1 cross-provider fix,

## Checked

### 1. The M4-1 F1 cross-provider fix — CLOSED, verified on BOTH sides
- `paymentErrors.ts:105-119` `assertNoBlockingAttempt` is genuinely GLOBAL:
  it is handed `findMany({ where: { orderId } })` (no provider filter) and
  blocks on ANY provider's `CONFIRMED` (→ `PaymentAlreadyConfirmedError`),
  any non-stale `PENDING`, and any `INITIATED` younger than
  `IN_FLIGHT_GRACE_MS`. It performs no DB access and selects no row to
  mutate — correct separation.
- The one provider-specific rule inside it, `isMpesaPendingStale`
  (`paymentErrors.ts:85-91`), is hard-gated on `row.provider === "mpesa"`,
  so a Stripe `PENDING` row can never be aged out by the 180 s M-Pesa
  ceiling. Confirmed by reading the predicate, not the comment.
- **Stripe side** (`paymentService.ts:304-377`): after the global assert,
  row selection is `existing.find(r => r.status === "INITIATED" && r.provider === "stripe")`
  (`:307`). Every mutation is by `initiated.id` (`:335`) or
  `prepared.paymentTransactionId` (`:444`, `:475`), and every `create` hardcodes
  `provider: "stripe"` (`:353`, `:369`). Traced all four write sites — the
  Stripe flow can no longer adopt or mutate an `mpesa` row.
- **M-Pesa side** (`mpesaService.ts:330-383`): same shape. Both sweeps filter
  `r.provider === "mpesa"` (`:338`, `:358`); `failRowForward` is called only
  with those ids; the `create` hardcodes `provider: "mpesa"`. Phase C's CAS
  (`:466-479`) is keyed on `prepared.paymentTransactionId`. Cannot touch a
  `stripe` row.
- **Cross-blocking still works, both directions** (the half that must NOT
  become provider-scoped): a live `stripe` `PENDING`/`INITIATED` row throws
  `PaymentAttemptInFlightError("stripe")` out of the M-Pesa flow, and a live
  `mpesa` row (< 180 s `PENDING` / < 120 s `INITIATED`) throws out of the
  Stripe flow. Covered symmetrically by
  `tests/test23:347,391` and `tests/test20:522`.
- Verdict: M4-1's tracked F1 is **actually closed**, not just claimed closed.

### 2. Crash recovery — genuinely "fail forward, new row", NOT replay
Traced `mpesaService.ts:358-383` directly. An orphaned `mpesa` `INITIATED`
row (reachable only when older than `IN_FLIGHT_GRACE_MS`, since anything
younger already threw in `assertNoBlockingAttempt`) is CAS'd to `FAILED`
via `failRowForward(..., "INITIATED", "stk_push_indeterminate", ...)`, which
is a guarded `UPDATE ... WHERE id = $1 AND status = 'INITIATED'` and writes
a `PAYMENT_SESSION_FAILED` OrderEvent only when `affected === 1`. Then a
**brand-new** row is created unconditionally with `idempotencyKey =
randomUUID()` (`:371-383`). There is no code path that reuses the orphan's
id or key — structurally different from `paymentService.ts:319-325`, which
deliberately does replay for Stripe. No second STK prompt can be triggered
from a crashed attempt. Correct for a provider with no idempotency key.

### 3. Daraja `Timestamp`/`Password` — TZ-independent, confirmed
`mpesa.ts:182-191`: `new Date(nowMs + 3 * 3600_000).toISOString()`, i.e. a
fixed +03:00 offset applied in epoch-millis space, then formatted with
`toISOString()` (always UTC by spec, unaffected by `process.env.TZ`). No
`getHours()`/`toLocaleString()`/`Intl` anywhere in the function, and no
ambient TZ read. Local dev on `Africa/Mogadishu` and Vercel on UTC produce
byte-identical output. The `passkey` is only ever consumed into a base64
digest here and never returned, logged, or included in an error.

### 4. Amount handling — ceil, never floor; never client-supplied
`mpesaService.ts:321`: `new Prisma.Decimal(order.totalAmount).ceil()` — ceil,
so rounding is always in the merchant's favour; an underpayment cannot be
silently accepted. The same `requested` value (not `order.totalAmount`) is
what is written to `PaymentTransaction.amount` (`:378`) and what is sent to
Daraja (`:435`, `Number(prepared.requested.toFixed(0))`) — traced both, they
are the same variable. `currency: "KES"` is hardcoded. The route's body
allowlist is exactly `{orderId, phoneNumber?}` (`route.ts:65-73`, unknown key
→ 400) so no amount/currency/shortcode can be supplied by the client.
Reconciliation is correctly scoped and made durable: `metadata.orderTotal`,
`metadata.amountRequested`, `metadata.roundingDelta` (`:470-476`), so the
over-collection is queryable rather than invisible.

### 5. Token cache and 401 retry
- Token value is **never** logged. The only log line is the fixed, valueless
  `console.log("[mpesa] oauth token refreshed")` (`mpesa.ts:154`). Grepped all
  of `src/` for `console.*` — no other site touches the token.
- `cache: "no-store"` is genuinely set on the OAuth fetch (`mpesa.ts:111`),
  alongside a bounded `AbortSignal.timeout`.
- The 401/403 invalidate-and-retry-once is **really implemented**, not just
  tested: `mpesa.ts:244-248` (`if (res.status === 401 || res.status === 403)
  res = await attempt(true)`), and `attempt(true)` sets `cached = null` before
  calling `getCachedAccessToken` (`:230-232`). Exactly one retry; a second
  401 falls through to the `!res.ok` branch and becomes a generic 409.
- Cache key includes `consumerKey` (`:133`), so a credential rotation cannot
  serve a token minted under the old key. `expires_in` that is NaN/≤0 is
  treated as immediately-expired rather than cached (`:148-151`) — fail-safe.
- No `NODE_ENV`/env-flag branch anywhere in `mpesa.ts` or `mpesaService.ts`:
  the mocking seam is a plain `fetchImpl` default parameter, so the test
  boundary cannot alter production behaviour.

### 6. Phone number (PII) and abuse control
- The normalized MSISDN appears in exactly one persisted place,
  `PaymentTransaction.metadata.phoneNumber` (`mpesaService.ts:472`). It is
  **not** in the `PAYMENT_STK_PUSH_SENT` OrderEvent payload (`:486-492` —
  provider / ids / amount only) and **not** in the response body (`:500-506`).
- The only log line carrying it is masked: `maskMsisdn` (`:156-159`) →
  `2547****NNNN`, used at `:459`. No unmasked phone number reaches any log.
- Rejected phone input never echoes the submitted value back
  (`mpesaErrorResponse` → fixed string, `:117-120`).
- Rate limiting is **genuinely wired**, not commented: `route.ts:43-50`,
  `checkRateLimit(\`mpesa-stk:${userId ?? getClientIp(request)}\`, {limit: 5,
  windowMs: 600_000})`, evaluated *before* body parsing, returning 429 with
  `Retry-After`. Combined with ownership + the 180 s in-flight block this is
  a real control over the `phoneNumber` override. See F4 for its limits.

### 7. Error responses — no leak
Traced `mpesaErrorResponse` (`mpesaService.ts:90-136`) case by case:
- `MpesaPushRejectedError` → 409 `{error: "M-Pesa could not send the payment
  prompt, please try again"}` — `err.code` / `err.providerMessage` are not
  referenced in the body at all. Daraja's `errorCode`/`errorMessage` go only
  into `PaymentTransaction.failureCode`/`failureMessage` (`:398-403`,
  truncated to 190/500 chars) and the masked server log.
- `MpesaUnavailableError` → 502, fixed string, no `err.message`.
- `OrderNotFoundError` → 404 generic body, orderId only in the server log
  (`:94`) — matches the M4-1 404-not-403 anti-oracle rule.
- No `requestId`-equivalent is ever constructed. `MPESA_CONSUMER_SECRET` and
  `MPESA_PASSKEY` are read at exactly two sites (`mpesa.ts:93`, `:208`), both
  consumed into a base64 blob; grepped — neither appears in any thrown
  message, response body, or log line. The "not set" errors name the
  variables, never the values.

### 8. Standard sweep
- **PCI scope:** no card data anywhere. Daraja's PIN entry happens on the
  handset; the route's body allowlist admits no PIN/PAN field and none is
  constructed. No finding.
- **Idempotency:** N/A for this item's outbound direction (no webhook handler
  is added here — HRH-50). The duplicate-*attempt* guard is item 1 above.
  Every status transition is a guarded CAS (`WHERE ... AND status = <expected>`)
  with an `affected !== 1` check (`:242`, `:480`), so a lost race is a no-op,
  never a double write.
- **Auth:** no hand-rolled credential/JWT/session table. Identity comes from
  `auth.api.getSession()` (`route.ts:35`) and the guest path from the
  cart cookie + the `CREATED` OrderEvent's `sessionId` (`mpesaService.ts:289-301`),
  identical to the verified M4-1 route. Ownership failure returns the same
  404 as a missing order — no existence oracle. No new admin surface.
- **Presence-check middleware:** N/A — this route does its own server-side
  session resolution in the Node runtime and does not rely on middleware.
- **Admin audit log:** no admin mutation in this diff. N/A.
- **Input validation:** strict key allowlist + type checks at the route
  (`:58-81`); `normalizeMsisdn` is anchored-regex allowlist validation
  (`:143-152`), not a sanitiser. Note this repo validates payment routes by
  hand rather than Zod, consistent with the already-verified M4-1 route —
  not a new divergence.
- **Injection:** every raw statement is a Prisma tagged template
  (`mpesaService.ts:233-241`, `:272-277`, `:466-479`); `orderId`, row ids,
  failure strings, the metadata JSON and `checkoutRequestId` are all bound
  parameters. No string concatenation into SQL. No finding.
- **Data residency:** `mpesaService.ts:309-311` hard-gates on
  `order.region === "KE" && order.currency === "KES"` *before* any network
  call, so no Ethiopia/Somalia order data can ever reach Safaricom's Kenyan
  endpoint. This is strictly better than M4-1's currency allowlist (whose
  pre-opened ETB/SOS entries were a finding there) — no equivalent issue here.
- **Secrets in env files:** `.env.example` and `.env.development` still carry
  `REPLACE_ME` for `MPESA_CONSUMER_KEY`/`MPESA_CONSUMER_SECRET`/`MPESA_PASSKEY`;
  the new `MPESA_MAX_AMOUNT_KES="150000"` is a policy limit, not a credential;
  `MPESA_SHORTCODE="174379"` is Safaricom's public sandbox paybill, not a
  secret. `.env.production.kenya` explicitly documents (`:15-16`) that all
  M-Pesa credentials live as Vercel project secrets and are not stored in the
  file — re-confirmed by reading the file in full during the F1
  re-verification. No real value introduced. No finding.

## Findings

### F1 — MEDIUM — RESOLVED 2026-08-30 (re-verified) — `MPESA_CALLBACK_URL` stale path in Kenya production config + operator runbook

**Original finding (first pass):** `.env.production.kenya:13` read
`MPESA_CALLBACK_URL="https://ke.hurbadhardware.com/api/payments/mpesa/callback"`
and `docs/DEPLOYMENT.md:90-91` instructed operators to set that same stale
path, while only `.env.example:61` and `.env.development:28` had been
corrected to `/api/webhooks/mpesa` — yet `FEATURES.md:2443` checked the box
"`MPESA_CALLBACK_URL` mismatch resolved" and the ADR (Decision 7) declares
`/api/webhooks/mpesa` canonical.

Why it mattered: `buildCallbackUrl` (`mpesaService.ts:207-215`) fails closed
only on "unset or not `https://`" — a well-formed URL pointing at a route
that will never exist passes validation, so Kenya production would have
handed Daraja a callback URL resolving to a 404. Every STK payment outcome
would be silently lost: the customer debited, `PaymentTransaction` stuck
`PENDING`, and HRH-50's stale sweep later marking it `FAILED`. A
money-taken-no-record path.

**F1 re-verification, 2026-08-30 — CONFIRMED FIXED.** After
`commerce-payments-engineer`'s fix pass I independently re-checked, reading
the files directly rather than trusting the builder's report:
1. `.env.production.kenya:13` now reads
   `MPESA_CALLBACK_URL="https://ke.hurbadhardware.com/api/webhooks/mpesa"`
   — correct canonical path, correct Kenya host, `https://` preserved (so
   `buildCallbackUrl`'s fail-closed guard still passes for the right reason).
   Read the whole file: no other stale path, and no credential value present.
2. `docs/DEPLOYMENT.md:90-91` now reads "Set `MPESA_CALLBACK_URL` to the
   deployed Kenya domain's webhook route
   (`https://ke.hurbadhardware.com/api/webhooks/mpesa`)" — the operator
   runbook matches the config.
3. Ran my own repo-wide greps rather than accepting the builder's claim:
   - `payments/mpesa/callback` — 10 hits remain, and I inspected the
     surrounding context of each. All are historical/narrative: `FEATURES.md`
     (:2445, :2456, :2571 — the criterion text and the fix write-up
     *describing* the old value), `docs/agents/run-state.md:160` (the

   - `MPESA_CALLBACK_URL` — the only three assignments in the repo are

F1 is closed. No blocking findings remain → STATUS raised to CLEAR.

### F2 — LOW (advisory, binding on HRH-50) — a stale `mpesa` PENDING row is bypassed globally but never cleaned up by the Stripe flow
Correct by design here, but it creates a window worth naming explicitly.
Once an `mpesa` `PENDING` row passes `MPESA_PENDING_STALE_MS`
(`paymentErrors.ts:34`), `assertNoBlockingAttempt` stops blocking on it, so a
Stripe attempt may proceed. `paymentService.ts` correctly does **not** sweep
it (provider-scoped mutation), so it remains `PENDING` indefinitely. If a
delayed Daraja callback then arrives after the Stripe payment confirmed, both
providers could report success for one order.

Not fixable in this item (no callback handler exists yet). Binding
requirement for HRH-50: before confirming an `mpesa` row, the callback
handler must take the `"Order" FOR UPDATE` lock and re-check that no
`PaymentTransaction` for that order — **any provider** — is already
`CONFIRMED`, and record a distinct OrderEvent if one is.

### F3 — LOW — duplicated staleness constant can silently diverge
`mpesaService.ts:41` defines a local `PENDING_STALE_MS = 180_000` that is
only exported for tests via `__TEST_ONLY__` (`:511`); the value the predicate
actually uses is `MPESA_PENDING_STALE_MS` in `paymentErrors.ts:34`. Editing
the `mpesaService.ts` copy would change what the tests assert without
changing behaviour — a test that agrees with itself. Import the constant
from `paymentErrors.ts` instead of redeclaring it.

### F4 — LOW — the anti-phone-spam rate limit is weakest for exactly the caller it targets
`route.ts:43` keys on `userId ?? getClientIp(request)`, and `getClientIp`
(`rateLimit.ts:80-85`) takes the first value of a client-supplied
`x-forwarded-for`. For a guest checkout (`userId === null`) the bucket key is
therefore attacker-chosen, so the 5-per-10-min backstop on the
`phoneNumber` override can be rotated away by varying the header; the
per-instance in-memory Map (`rateLimit.ts:10-16`) further weakens it on
Vercel. Ownership and the in-flight predicate remain, and they cap prompts
per *order*, but an attacker can create multiple guest orders.

Non-blocking (the ADR calls this a backstop, not the primary control), but
since Decision 8 leans on it specifically to prevent ringing a stranger's
phone, it should prefer a platform-set header (`x-vercel-forwarded-for`) over
the client-settable `x-forwarded-for`, and the guest bucket should be keyed
on the cart session id rather than the IP. I could not empirically confirm
Vercel's header-overwrite behaviour without running code — see Known-limits.

### F5 — LOW — only the first stale row of each status is swept
`mpesaService.ts:338` and `:358` use `.find(...)`, so if an order somehow
accumulates two orphaned `mpesa` `INITIATED` (or stale `PENDING`) rows, only
one is failed forward; the rest linger in a non-terminal state forever.
Harmless for blocking (they are already past the grace window), but it leaves
permanently misleading rows for reconciliation and for HRH-50's sweeps.
`.filter(...)` + loop would close it.
