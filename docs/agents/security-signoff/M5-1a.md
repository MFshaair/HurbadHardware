## Checked

- **PCI scope: checked, no finding.** No card data of any kind enters this
  code. The email body is built exclusively from `Order`/`OrderItem` snapshot
  columns and `ProductVariant.name`
  (`orderNotificationService.ts:188-209,250-264`); the Stripe `session` /
  `PaymentIntent` objects are never passed into `dispatchOrderConfirmationEmail`
  (both dispatch sites pass only `orderId` — `paymentWebhookService.ts:161,217,249`,
  `mpesaCallbackService.ts:615,703,737`). No PAN-shaped value, `last4`, or
  provider credential is rendered, logged, or written to `OrderEvent.payload`.
  The SendGrid request body (`emailService.ts:80-94`) contains only recipient,
  subject, the two content parts, and `custom_args: { orderId, orderNumber }`.

- **Payment idempotency: checked, no finding.** Verified specifically:
  - The claim (`claimDispatch`, `orderNotificationService.ts:64-82`) takes
    **exactly one** lock (`SELECT id FROM "Order" ... FOR UPDATE`), performs
    **zero** network I/O inside the transaction (only `$queryRaw`,
    `orderEvent.findFirst`, `orderEvent.create`), and **commits before** the
    send. The `emailService.send()` call is at line 266, structurally outside
    and after the `db.$transaction` block at 65-81. Requirement 2 satisfied —
    no SendGrid latency is ever held under an `Order` row lock.
  - A redelivery hitting the `duplicate`/resume arms finds the existing claim
    and returns at line 244-248 with zero sends and zero writes. Concurrency is
    serialised by the `Order FOR UPDATE`, not by a read-then-write race.
  - Nothing in this module writes `Order.paymentStatus`,
    `PaymentTransaction.status`, `InventoryReservation`, or
    `RegionalInventory`. Grepped and confirmed: the only writes are
    `orderEvent.create` and `orderEvent.update`.
  - `maybeDispatchEmail` is `void dispatch...()` in both handlers
    (`paymentWebhookService.ts:39-41`, `mpesaCallbackService.ts:37-39`) and
    `dispatchOrderConfirmationEmail` cannot reject (see next bullet), so no
    email outcome can abort, delay, or roll back a confirm.
  - **Requirement 1 traced line by line.** Every `await` reachable from
    `dispatchOrderConfirmationEmail` sits inside the `try` at
    `orderNotificationService.ts:314-320`: `db.order.findUnique` (211),
    `writeFailedEvent` (221/228/239/289), `claimDispatch` (243),
    the synchronous `renderOrderConfirmationEmail` (250, can throw on a null
    Decimal — still inside the try), `sendWithRetry` (266, whose every
    `emailService.send` is itself wrapped at 155-173 and whose backoff
    `setTimeout` promise cannot reject), and `updateClaimPayload` (280/288).
    `AbortSignal.timeout(...)` is constructed inside the inner try. The
    scheduler invocation itself is additionally wrapped at 323-329, so even a
    misused `after()` outside request scope cannot propagate. The function is
    genuinely unrejectable; test 13 (a-e) covers exactly the five cases
    requested (no recipient, unconfigured key, 500, raw network throw,
    non-existent orderId) with `resolves.toBeUndefined()`.
  - **Requirement 3 (`PAYMENT_CONFIRMED_STOCK_UNAVAILABLE`) confirmed in both
    files.** `paymentWebhookService.ts:261-300` (`recordStockUnavailable`) and
    `mpesaCallbackService.ts:745-775` contain **no** `maybeDispatchEmail` call
    on any return path, and the `already_flagged` short-circuits
    (`paymentWebhookService.ts:164-167`, `mpesaCallbackService.ts:625-626`)
    return before any dispatch. I also walked the sibling terminal arms the
    M4-2b learning warns about: the `PAYMENT_AMOUNT_MISMATCH` arm
    (`mpesaCallbackService.ts:627-628`, 787-798) and the
    `PAYMENT_DOUBLE_PAYMENT_DETECTED` arm (618-624, 634-635) also return
    without dispatching — correct, since `Order.paymentStatus` is not
    `CONFIRMED` on any of them. Every one of the five dispatch sites is
    guarded by a freshly re-read `order.paymentStatus === "CONFIRMED"` from
    the DB, never by an in-memory assumption. Test 3 covers the stock-gone
    path for both providers.
  - **Requirement 6 (deadline guard) confirmed.** The zero-budget check at
    `orderNotificationService.ts:235-241` runs *before* `claimDispatch` at 243
    and returns, so a past `deadlineAt` produces a `no_time_budget` FAILED row
    and **no** claim — matching Decision 5's "do not write the claim". Test 18
    asserts both zero fetch calls and zero `ORDER_CONFIRMATION_EMAIL_DISPATCHED`
    rows. See advisory A4 for the narrow residual window.

- **Auth: checked, no finding.** No credential field, JWT, session table, or

- **Admin audit log: checked, N/A — no finding.** This diff contains zero admin

- **Input validation: checked, no finding.** No new user-facing input surface

- **XSS in the template (requirement 4): checked, no finding.**

- **PII handling (requirement 5): checked, no finding.** I grepped every

## Requirement 7 — the `inlineAfterResponse` deviation: NOT a hardening blocker

Assessed directly. `inlineAfterResponse` (`emailService.ts:192-194`) is
`(task) => { void task(); }` — genuinely fire-and-forget, and the builder is
right that this matches the ADR's own type signature *and* the ADR's own code
block (`M5-1a-order-confirmation-email.md:40` literally writes `void task()`);
only the ADR's prose comment says "run inline and await". The ADR contradicts
itself, exactly the class my learnings file already records ("a code comment
restating an ADR rule can be false against its own file").

It is **not** currently a production risk, because I verified every production
entry point injects a real scheduler: `stripe/route.ts:50`,
`mpesa/[token]/route.ts:70`, and `cron/mpesa-reconcile/route.ts:62-68` all
pass `schedule: after`, and those are the only three callers of
`handleStripeWebhookEvent` / `handleMpesaCallback` / `runMpesaReconciliation`
in `src/` (grepped). The default is reached only by tests, scripts and seeds.
The residual — a killed invocation losing the email — is precisely the
at-most-once limitation the ADR already documents. **Correctly scoped as an
accepted known-limit; no fix required.** The misleading comment is A1.

## Advisories (non-blocking, for the builder/orchestrator to record)

**A1 — LOW (documentation accuracy).**
`src/lib/emailService.ts:189-191`. The JSDoc on `inlineAfterResponse` says
"run inline and await"; the body (:192-194) does not await. The comment is
false against the three lines below it. No production caller relies on the
default today, but the next author who adds a serverless caller and omits
`emailDeps` will get exactly the silently-dropped-work failure mode ADR
Decision 1(a) rejected, on the strength of this comment. Recommend rewording
to "fire-and-forget; production/serverless callers MUST inject `after()`",
and correcting the ADR's own prose at `M5-1a-...md:38-41` so the two agree.

**A2 — LOW (ops mislabelling).**
`src/lib/orderNotificationService.ts:126-129`. `classifyError` returns
`reason: "permanent_${status}"` for *any* `EmailSendError` carrying a status,
including retryable `429`/`5xx`. Reachable: if the loop breaks on the deadline
guard (:149-152) at attempt >= 2, `sendWithRetry` returns `reason: lastReason`
(:176) — so a transient `500` is durably recorded as `permanent_500` in
`ORDER_CONFIRMATION_EMAIL_FAILED`. Because `writeFailedEvent`'s dedup guard is
keyed on `reason` (:97-106), the mislabel also changes dedup grouping. Suggest
deriving the reason from `retryable` (`retryable_${status}` vs
`permanent_${status}`). No money-path effect; ops-queue readability only.

**A3 — LOW (non-atomic dedup on the no-claim failure paths).**
`src/lib/orderNotificationService.ts:108-122`. `writeFailedEvent` is a
find-then-create with no lock and no unique constraint, unlike the claim path
which is correctly serialised under `Order FOR UPDATE`. Two concurrent confirm
invocations (the ADR's own test-6 scenario) both hitting `no_recipient` /
`not_configured` / `no_time_budget` can both find nothing and both insert,
producing duplicate FAILED rows. Cosmetic — no constraint is violated, no
send is duplicated (the send path is claim-protected).

**A4 — LOW (residual claim-then-zero-attempts window).**
`src/lib/orderNotificationService.ts:235-243` vs `:148-152`. The pre-claim
budget guard is correct, but `claimDispatch` (a DB round trip) runs between
that guard and `sendWithRetry`'s own re-check. If the claim transaction
consumes the remaining slack, the loop breaks immediately with `attempts === 0`
and the claim has **already** been written — the exact state Decision 5's
"do not write the claim" rule exists to prevent, permanently suppressing that
order's email with no retry path. The window is very narrow (the guard must
pass by less than the claim's own latency) and the outcome is a durable,
queryable `no_time_budget` FAILED row, so it is detectable rather than silent.
Suggested hardening: when `sendWithRetry` returns `attempts === 0`, delete the
just-created claim row (it is this invocation's own, and the id is in hand at
:243) so a later redelivery can retry.

**A5 — ADVISORY (data residency, needs recording not fixing).**
`src/lib/emailService.ts:63`. `https://api.sendgrid.com/v3/mail/send` is a
US-terminated endpoint. Every send transmits the customer's email address plus
the full order contents (order number, variant names, quantities, unit and
line prices, totals) out of the `eu-west-2` (London) region that
`run-state.md`'s active decisions name as the Kenya/Somalia data location.
The ADR does not address this at all. Not blocking for Kenya (same class
already accepted for Stripe, and Ethiopia/Somalia are out of horizon), but it
belongs in the standing residency escalation that already flags UK-GDPR
equivalence as unverified — so it is named now rather than discovered at the
Somalia launch. Also note the ADR's own open item: no DPA/sub-processor entry
exists for SendGrid.
