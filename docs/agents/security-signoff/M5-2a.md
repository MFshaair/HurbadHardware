## Round 2 verdicts

### F1 (MEDIUM) — GENUINELY FIXED

`src/lib/adminAuditLog.ts:69-75` now fails closed before any write:

```ts
if ("$transaction" in tx) { throw new Error("writeAdminAuditLog() must be called with the `tx` handle …"); }
```

I did not accept the "the deny list strips `$transaction` from a real
`tx`" claim — I verified all three legs of it in Prisma's own source:

1. **The deny list contains `$transaction`.**
   `runtime/edge.d.ts:725`:
   `declare const denylist: readonly ["$connect", "$disconnect", "$on", "$transaction", "$extends"]`,
   and `:1976` `ITXClientDenyList = (typeof denylist)[number]`.
2. **A genuine `tx` handle really does answer `false` to the `in`
   operator — not merely `undefined` on property access.** This was the
   one way the fix could have been silently wrong (a proxy that returns
   `undefined` from its `get` trap but leaves `has` at the default would
   make `"$transaction" in tx` **true** for a real `tx`, inverting the
   guard and breaking every future admin mutation). It is not wrong.
   `_createItxClient` builds the transaction client as
   `createCompositeProxy(…, [removeProperties(itxClientDenyList)])`;
   `removeProperties` returns a layer declaring
   `getKeys() { return keys }`, **`has() { return false }`**, and
   `getPropertyValue() { return undefined }`; and the composite proxy's
   own `has` trap is
   `if (overwrittenKeys.has(prop)) return true; const layer = keysToLayerMap.get(prop); if (layer) return layer.has?.(prop) ?? true; return Reflect.has(target, prop)`.
   `$transaction` is a layer key, and `overwrittenKeys` is populated only
   by the proxy's `set`/`defineProperty` traps (nothing assigns
   `$transaction` onto an itx client), so the trap resolves to the layer's
   explicit `has() === false`. `"$transaction" in tx` is `false` for a
   genuine transaction handle.
3. **The top-level client really does answer `true`.** `src/lib/db.ts`
   exports a plain, non-`$extends`-ed `PrismaClient`; the client proxy's
   `has` trap falls through to `Reflect.has(target, prop)` on the real
   instance (its `getPrototypeOf: () => Object.prototype` override does
   not affect `Reflect.has` against the target), so `$transaction`
   resolves on the prototype chain → `true` → throw.

So the guard is a reliable discriminator and closes exactly the gap F1
described (a `PrismaClient` being structurally assignable to
`Omit<PrismaClient, ITXClientDenyList>`). The four pre-existing
real-transaction tests (`test28:79, 103, 125, 147`) are themselves the
false-positive regression test for leg 2.

**The new test is non-trivial.** `test28:168-185` calls
`writeAdminAuditLog(db, {...})` with the full `PrismaClient` and asserts
`.rejects.toThrow(/db.\$transaction/)` **and** that zero `AdminAuditLog`
rows exist for that `adminId`. Delete the guard and the call resolves
successfully and commits a row — both assertions fail. The thrown
message contains the literal `db.$transaction(async (tx) => ...)`, so the
regex matches; the helper is `async`, so the synchronous `throw` surfaces
as a rejection, which `.rejects` handles correctly. Nothing about this
test can pass by construction.

Residual (recorded, not blocking): the guard proves "this is *a*
transaction handle", not "this is *the* transaction handle of the
mutation being logged" — passing a `tx` from a different concurrent
transaction would still pass. Unavoidable at this layer; M5-2b/c/d's
required caller shape (helper called inside the same
`db.$transaction(async (tx) => …)` body as the mutation) remains a
by-eye check at each call site. Also note the guard's correctness is
coupled to a Prisma internal (`removeProperties`' `has` trap). If a
future Prisma upgrade drops that trap the guard would start rejecting
genuine `tx` handles — loud and fail-closed, and the four existing
transaction tests catch it immediately. Acceptable direction.

### A1 (LOW) — FIXED

`src/lib/adminAuth.ts:71, 80, 132` now redirect to
`/auth/login?reason=admin_no_session`, and `src/middleware.ts:29`
redirects to a bare `new URL("/auth/login", request.url)` with no query
string — verified by reading both files, not by trusting the claim. The
two test outcomes are now genuinely distinguishable:
`test28:369-378` (no cookie) asserts
`url.searchParams.get("reason")` is **null**; `test28:380-401` and
`:403-422` (forged cookie) assert it is **`admin_no_session`**. Since
only the Node-runtime page gate can emit the marker, a future better-auth
change that made middleware reject the forged value would now make the
forged-cookie test **fail** rather than silently degrade into a second
no-cookie test — which was exactly A1's residual risk. Grepped the repo:
`admin_no_session` appears only in `src/lib/adminAuth.ts` and
`tests/test28-*`.

No new information disclosure. The marker is a fixed constant — no user
id, email, role, session id, token, or timing data is encoded in it — and
`src/app/auth/login/page.tsx` never reads `useSearchParams()`/`searchParams`
at all, so the value is not rendered, stored, or reflected anywhere (no
reflected-XSS or log-injection surface; it only ever exists in the URL
bar and the server access log). The one behavioural delta is that an
unauthenticated caller who sends a garbage cookie to `/admin` learns the
`/admin` prefix has an admin-specific gate. That does not weaken the
404-not-403 property the ADR actually cares about — that property is
about an authenticated **CUSTOMER**, who still gets `notFound()` from
`requireAdminRole()` (`adminAuth.ts:88-90`) and never sees this marker —
and the pre-existing `?reason=admin_timeout` on the same page already set
this precedent in round 1. Judged benign.

### A2 (LOW) — FIXED, substitute proof accepted

`test28:632-641` replaces the decorative `Session.updatedAt` backdating
with `readFile` on `src/app/profile/page.tsx` and
`src/app/dashboard/orders/page.tsx`, asserting neither matches
`/adminAuth/`. I read both files: each imports only
`next/headers`, `next/navigation`, `@/lib/auth`, `@/lib/db` (plus
view-layer helpers), does its own `auth.api.getSession()` +
`if (!session) redirect("/auth/login")`, and references neither
`adminAuth`, `ADMIN_IDLE_TIMEOUT_MS`, nor `adminSessionActivity`. So the
assertion is true today and is genuinely falsifiable — adding the import
turns the test red — unlike the old leg, which `@updatedAt`
(`prisma/schema.prisma:619`) made impossible to fail. That is the right
shape of substitute: it proves the *absence of the lever* rather than
faking elapsed time against a lever that does not exist.

Scope limits, recorded not blocking: it is a two-file source check, so a
third customer-reachable page (e.g. `dashboard/orders/[orderId]`) or an
indirect/transitive import would not be caught, and a mere comment
mentioning `adminAuth` would trip it (fail-safe direction). The
independent repo-wide grep for `adminAuth`/`adminSessionActivity`
importers I ran in round 1 — only the four files under `src/app/admin/` —
still holds and I re-ran it this session.

The other two legs of that test are intact and remain sound:
`test28:610-616` asserts the CUSTOMER session's
`expiresAt - createdAt ≈ 7 days` (60s tolerance) against the row selected
by `orderBy: { createdAt: "desc" }`, and `test28:618-619` asserts
`adminSessionActivity.findUnique({ where: { sessionId } })` is null. The
`/profile` and `/dashboard/orders` 200s before and after (`:601-604`,
`:645-648`) are unchanged. Neither was the broken part and neither was
touched.

  at the gate.
